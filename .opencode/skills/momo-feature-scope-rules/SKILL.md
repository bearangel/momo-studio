# Momo Studio 功能修改全面性工作流

改任何既有功能前必须走完本工作流。核心教训：**「补了被指出的那一个点」≠「完成了功能修改」**——功能沿消费面铺开，只补单点 = 给下一个人埋死路；**只改生效层 ≠ 完成状态翻转**——每个读该状态做展示的地方都是消费面。条文靠自觉，工作流靠产物：每一步必须留下可验证的产物，没有产物 = 没做。

## 五步工作流

### W1 机械枚举（不许凭记忆列行）

跑三锚 grep，输出就是消费点清单。锚错了枚举必漏——三锚缺一不可：

```bash
# 锚① 能力名/资源名消费点（代码引用面：import / SQL 列 / IPC 通道名）
grep -rn "<能力名或资源类型名>" electron/src renderer/src --include="*.ts" --include="*.tsx" | grep -v "\.test\."

# 锚② 展示动词面（一切把该能力「列出来给人看/选」的位置）
grep -rnE "list[A-Z][a-zA-Z]*|候选|选择器|resource\.list|/ *命令|slash" electron/src/main/resource electron/src/main/plugin renderer/src --include="*.ts" --include="*.tsx" | grep -v "\.test\."

# 锚③ 状态读取点（仅状态翻转类改动：启停/默认值/可见性语义变化时必跑）
# <判定函数> = 本次翻转的状态判定函数（如 isPluginEnabled / getMcpConfig.enabled）
grep -rn "<判定函数名>" electron/src renderer/src --include="*.ts" --include="*" | grep -v "\.test\."
```

- **产物**：消费点清单（文件:行 + 一句分类：数据通路 / 展示面 / 编辑器 / 装配链）
- **完成判定**：三锚都跑过且输出已收集。状态翻转类改动漏锚③ = 本步未完成。

### W2 矩阵落盘

矩阵写入 `.omo/feature-matrices/<日期>-<功能名>.md`（跨会话可审计；没落盘 = 设计不完整，不得进入实现）。

- **行** = W1 清单逐点 + 四类展示面 checklist 逐类过（不许漏类）：
  1. 资源目录页（资源库各类型页签）
  2. 各选择器候选列表（成员编辑 MCP/Skill/工具页签、工作空间配置页）
  3. 命令引用入口（会话输入框 / 命令、@ 引用）
  4. 各编辑器（定义编辑 / 成员编辑 / 工作空间配置）
- **列** = 对象生命周期（**新建 / 存量 / builtin 只读**）
- 每格填「改 / 不改 + 理由」，空格必须写理由不许留白
- **产物**：矩阵文件
- **完成判定**：四类展示面各有至少一行（哪怕裁定为「不改」）。

### W3 diff 反查

把 W1 清单与 W2 矩阵行做差集——**查到却不在矩阵里的点，逐个写「改/不改+理由」追加进矩阵**（落「反查」节）。

- **产物**：矩阵「反查」节（可为空，但必须显式写「反查差集为空」）
- **完成判定**：差集为零或差集内每点均已裁定。

### W4 放行门禁（8 项是非题，任一「否」→ 回 W1/W2）

逐项回答，答案写进矩阵文件「门禁」节：

1. / 命令类引用入口已逐个裁定？（是/否 + 矩阵行号）
2. 各编辑器（定义/成员/工作空间配置）的候选列表展示已逐个裁定？
3. 资源目录各页签对本次变更的展示态已裁定？
4. 存量对象的改造/兼容路径已写明？
5. builtin / 只读对象的管理通道已回答（成员 deltas 覆盖是既有模式，优先复用）？
6. 状态翻转类：每个状态读取点（锚③结果）都已裁定新语义下的行为？
7. 生效层（装配/运行时）与可见层（展示/候选/引用）**两层分别**有裁定？
8. 验收锚点含至少一个存量对象 + 一个 builtin 只读对象场景？

### W5 验收回填

矩阵每格回填「已验证」证据（测试名 / 截图 / 日志行号）。只测新建路径不算完成。

- **产物**：矩阵每格有证据或显式「待验证」标注 + 对应验收项
- **完成判定**：W4 第 8 条所列场景的证据齐备。

## 工作流背后的原则（为什么）

1. **消费面矩阵先行**——不落盘的矩阵等于没有矩阵
2. **新建-存量对称律**——「新建可配 X」必须同时回答「存量如何获得/管理 X」
3. **注册类与状态翻转全覆盖**——新增资源类**或翻转状态语义**时，枚举全部消费方逐一接入，不接的显式记录理由
4. **只读对象覆盖通道**——builtin/只读对象经成员 deltas 管理，优先复用既有模式
5. **验收含存量场景**——存量与 builtin 场景锚是完成定义的一部分

## 案例摘要

- **插件工具门控（2026-10-17）**：`deniedTools` 只落了 DefinitionEditor——成员编辑无插件面、builtin 定义只读 → 系统预设完全无法管理插件工具，「看不见也管不了」。修复：deltas 行模型扩 `plugin_tool` + 成员级 add/remove 覆盖 + MemberEditDialog 复用公共组件。违反原则 1/2/4/5。
- **插件停用翻转（2026-10-21）**：spawn 侧生效过滤全做对，但会话 / 命令选择器、成员编辑 MCP/Skill 候选列表、资源库各页签的**展示面全漏**——矩阵以「我改动的面」为中心构造，而非「状态的影响面」；grep 锚用了功能名而非**状态读取点**（isPluginEnabled 调用方），枚举必然漏展示层。教训：**生效性 ≠ 可见性**；状态翻转类改动的 grep 锚 = 状态判定函数的全部调用方。本工作流的锚③与门禁第 6/7 条即由此沉淀。
