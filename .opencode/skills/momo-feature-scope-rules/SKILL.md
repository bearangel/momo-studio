# Momo Studio 功能修改全面性规则

改任何既有功能前必须检查。教训：**「补了被指出的那一个点」≠「完成了功能修改」**——功能沿消费面铺开，只补单点 = 给下一个人埋死路。

## 五条铁律

1. **消费面矩阵先行**。功能修改的设计/计划必须产出一张矩阵：**行** = 该功能的全部消费面（每个 UI 入口 / IPC 通道 / 数据通路 / 文档与帮助），**列** = 对象生命周期（**新建 / 存量 / builtin 只读**），格子填「改 / 不改 + 理由」。没有矩阵 = 设计不完整，不得进入实现。
2. **新建-存量对称律**。「新建对象可配 X」的能力，必须同时回答「**存量对象**如何获得 / 管理 X」。只做 create 路径不算完成。
3. **注册类全目录覆盖**。新增一类资源（工具 / MCP / skill / 面板 / 配置项）时，必须枚举**全部消费方**（资源目录、各选择器、各编辑器、装配链）逐一接入；不接的显式记录理由，不允许遗漏沉默。
4. **只读对象覆盖通道**。能力面变更必须回答「**builtin / 只读对象**怎么管理」——成员 deltas 覆盖（assignment-capabilities 的 add/remove 行模型）是既有模式，优先复用。
5. **验收含存量场景**。验收锚点必须至少覆盖一个**存量对象改造路径**（builtin 或已存在对象经新入口完成变更并生效），不许只测新建路径。

## 案例摘要

- 插件工具门控（2026-10-17）：`deniedTools` 只落了 DefinitionEditor（创建 + 编辑自定义定义）——智能体页成员编辑（MemberEditDialog）无插件面，builtin（Smith 等）定义只读 → 系统预设**完全无法管理插件工具**；而底层装配对所有 agent 默认注入，「看不见也管不了」= 用户感知「没法添加」。违反铁律 1/2/4/5。
- 修复实践：deltas 行模型扩 `plugin_tool` 类型（零迁移）+ 成员级 add/remove 覆盖（removed 胜出的保守语义与 tools 对齐）+ MemberEditDialog 插件分组复用公共组件。

## 标准动作

```
1. 改功能前：grep 该功能名 / 资源类型名的全部消费点，落消费面矩阵进计划
2. 矩阵列必含「存量」「builtin 只读」两列——空格必须写理由不许留白
3. 新资源类型：列全部注册表/目录/选择器/编辑器清单，逐一勾选接入
4. 验收锚点写存量场景：已存在对象（优先 builtin）经新入口改一次 → 运行时生效
5. 完成后自检：矩阵每格回填「已验证」证据（测试名 / 截图 / 日志）
```
