# Momo Studio UI 变更预览规则

动 renderer 任何用户可见的东西之前，先过本规则的分级判定。目的：**方向错误拦在预览阶段，不浪费在实现之后**。

## 分级判定（先判级，再动手）

| 级别 | 判定条件 | 动作 |
|---|---|---|
| **P1** | 布局变更（挪动 / 重排 / 增删区块）；新组件、新页面、新视图；多方案取舍（≥2 种合理设计）；视觉风格修改但用户未指定确切值（「更紧凑」「更现代」类模糊诉求） | **前置静态预览门禁**：出 HTML mockup → 用户明确同意 → 才写产品代码 |
| **P2** | 三条件**同时**满足：①用户指令给出确切目标值（token 名 / 字号 / 图标名 / 具体文案）②单组件范围 ③不引起布局位移 | 跳过前置预览，直接实现，**事后截图验收** |

- **混合任务按最高级别走**：一次任务里 P2 小改 + P1 大改 → 整体按 P1。
- **UI bug 修复不触发本规则**：走 `momo-debug-rules`，修完截图证明修复效果即可。
- 判级拿不准 → 按 P1 处理（宁可多一轮确认，不做返工）。

## 静态预览制作规范（P1 门禁）

1. **形态**：独立无构建 HTML 文件，落 `.omo/previews/<topic>.html`（`.omo` 已 gitignored——预览绝不入库、不进 workspace）。
2. **保真度铁律**：从 `renderer/src/styles/globals.css` 复制真实 CSS 变量（`:root` 明亮 + `.dark` 暗黑），语义对照 `docs/dev/design-system.md`。预览里每个颜色 / 字号 / 间距都用项目真实 token——编造色号 = 用户确认的是假方案，实现时还得再猜一遍。
3. **明暗双主题并排展示**：只展示单一主题的预览无效（明暗差异是高频翻车点）。
4. **before/after 对比**：变更区域改动前后并排；新页面 / 新组件展示完整 after 态；多方案取舍时并排展示全部候选。
5. **真实感 mock 数据**：填充接近真实长度的中文文案、状态、头像，不画「示例文字」空壳——用户要判断的是实际效果。
6. **静态近似边界**：动效 / hover / 展开态用多状态并排呈现，不写交互 JS；图标用内联 SVG 近似（lucide 图标路径）；字体系统回退即可（颜色 / 布局 / 间距保真优先）。
7. **交付与门禁**：macOS 主机 `open` 打开预览文件（容器场景告知路径），然后**停下等用户明确答复**。未确认 = 不写产品代码；用户提修改意见 → 改预览 → 再确认。

## P2 事后验收

实现完成后对真实 app 截图（`pnpm dev` + 浏览器截图；容器内 xvfb 截图），贴给用户对照指令确认。衔接内置 `visual-qa` 技能执行。

## 反模式（禁止）

- ❌ P1 级变更跳过预览直接实现——「设计很显然」不是跳过理由
- ❌ 预览用 Tailwind 默认色阶 / 编造色号，而非项目真实 token
- ❌ 预览只画空壳占位——用户无法据此判断实际效果
- ❌ 只展示明亮或暗黑单一主题
- ❌ 用户确认方向后又大改视觉、不二次确认——方向变更回到预览门禁
- ❌ 「预览已确认」当作跳过事后验证的理由——P1 实现完同样要截图对照预览
