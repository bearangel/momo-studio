# 2.0.0 P5「升级体验 + 发布收尾」实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 兑现 spec §8 升级路径（旧库检测 → 自动全量导出 + 备份 → 全新空库 + 首启提示）并将版本号升至 2.0.0 完成发布收尾。

**Architecture:** 主进程在 runMigrations **之前**检测旧库（schema_migrations 已应用最大版本 < 23 即 1.x 库）——此刻应用尚未打开 DB，可安全以只读连接导出旧数据（**用旧列名查询**：room_id/bot_matrix_user_id 等 pre-v23 schema）后改名备份，再走正常初始化建新库。导出物落 `upgrade-export-<时间戳>/`（每房间 Markdown + agent-definitions.json），kv 标记驱动 renderer 首启一次性提示。零用户交互阻塞启动（自动导出比交互式选择更安全——备份保留不删除）。

**Tech Stack:** 既有栈，零新增依赖。

**上游 spec:** §8（升级路径）+ §10（DoD）；决策 D5（完全重新开始）。
**控制器裁定（入交付说明）:** ① spec 的「提示 + 提供导出」落为**自动导出 + 首启提示**（导出目录路径在提示中告知），不做启动期交互式对话框——避免窗口未就绪时的控制流分叉，且备份保留优于确认后删除；② 版本号三处 package.json 统一 2.0.0。

## Global Constraints

- Node 20（`export PATH=/home/ai-agent/.nvm/versions/node/v20.20.2/bin:$PATH`）；pnpm `npx pnpm@9.0.0`。
- TypeScript strict：禁止 `any` / `@ts-ignore` / `as any`。注释中文；Conventional Commits。
- **旧库检测必须发生在 runMigrations 之前**（迁移会物理改造 schema，之后旧列名查询失效）。
- 导出查询使用 **pre-v23 列名**（messages.room_id / agent_assignments.bot_matrix_user_id 等）——该模块仅在升级路径执行，永不与新 schema 交互。
- 备份采用**改名**（state.db → state.db.legacy-v1.bak，含 -wal/-shm 若存在），绝不删除用户数据。
- 每任务 TDD；门禁 = 焦点测试 → 所属 workspace 全测 + typecheck 双 clean。

### Task 1: 旧库检测 + 自动导出 + 备份重置（主进程）

**Files:**
- Create: `electron/src/main/upgrade/legacy-detect.ts`
- Create: `electron/src/main/upgrade/legacy-export.ts`
- Create: `electron/src/main/upgrade/legacy-upgrade.ts`（编排：detect → export → backup → 标记）
- Modify: `electron/src/main/index.ts`（boot 链在 runMigrations 前插入 `runLegacyUpgradeIfNeeded()`）
- Modify: `electron/src/main/storage/db.ts`（无需改——检测自带只读连接；确认 getDb 懒加载语义不被破坏）
- Test: `electron/tests/upgrade/legacy-upgrade.test.ts`

**Interfaces:**
- Produces:
  - `detectLegacyDb(dbPath: string): { legacy: boolean; appliedMax: number }`——文件不存在或无 schema_migrations 表 → `{ legacy: false, appliedMax: 0 }`；max ≥ 23 → 非旧库；1 ≤ max < 23 → 旧库。
  - `exportLegacyData(dbPath: string, outDir: string): { sessionCount: number; agentDefCount: number }`——只读打开，查询旧列名：
    - 会话导出：旧库 rooms 信息不可得（Matrix 已逝）——直接按 `SELECT room_id, sender, event_type, body, created_at FROM messages WHERE event_type='m.room.message' ORDER BY room_id, created_at` 分组，每组写 `sessions/<room_id 安全化>.md`（头部注明 room_id 原值 + 条数 + 时间范围；正文复用 markdown-exporter 的 formatRoomToMarkdown 若签名兼容，否则手写极简模板——实现者核对后择一，报告说明）。
    - agent 定义：`SELECT name, slug, system_prompt, icon_emoji, description, default_tools, source FROM agent_definitions`（旧列名核对：v1.7 schema——实现时以 migration v1-v22 源码为准）→ 写 `agent-definitions.json`（数组 + meta）。
  - `runLegacyUpgradeIfNeeded(): Promise<string | null>`——编排：resolveDbPath() → detect → 非旧库返回 null；旧库：建 `upgrade-export-<YYYYMMDD-HHmmss>/`（resolveUserDataDir() 下）→ exportLegacyData → close 只读连接 → 改名 state.db(+wal/shm) → `.legacy-v1.bak` 后缀 → kv_store 写 `legacy_upgrade_notice`（注意：此刻新库未建——标记写入延迟到 runMigrations 之后由 index.ts 顺序执行：runLegacyUpgradeIfNeeded 返回 exportDir，index.ts 在 runMigrations 后写 kv）→ 返回 exportDir。单条失败（导出异常）**不阻塞升级**（log warn 继续备份重置——旧数据在备份里不会丢）。
  - boot 接线：main/index.ts 在 runMigrations 之前 `const legacyExportDir = await runLegacyUpgradeIfNeeded()`；runMigrations 后若非 null → kv 写标记 + log。
- 测试：临时目录构造 v22 库（applyUpToVersion 模式，migration v22 为最新）+ 种子数据（messages 两房间若干条 + agent def 两条）→ 跑编排 → 断言：导出目录两 .md 含正文与元信息头；agent-definitions.json 两条；state.db 已改名 .bak；原文件路径重新初始化后 schema_migrations 含 24；kv 标记路径正确（编排返回值）。非旧库（新库/无库）→ null 且零副作用。

- [ ] **Step 1: 失败测试** → **Step 2: RED** → **Step 3: 实现** → **Step 4: electron 全套 + typecheck** → **Step 5: Commit** `feat(upgrade): 旧库检测与自动导出——v1.x 数据 Markdown/JSON 落盘 + 备份重置`

## 风险与缓解

- **旧列名漂移**：导出查询列名以 migrations v1-v22 源码为唯一事实（实现时逐条核对，不凭记忆）；测试构造的 v22 库本身就是防漂移锚。
- **WAL 残留**：改名必须连带 -wal/-shm（若存在），否则备份不完整——测试覆盖有 WAL 场景（写入后不 checkpoint 再改名）。
- **boot 时序**：检测/导出/改名全部先于 getDb 首次调用（懒加载语义保护）；index.ts 接线顺序单测覆盖（编排返回值与 kv 写入分离的原因即此）。
