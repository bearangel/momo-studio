## 0. 摘要

v1.1 不引入新架构，聚焦 **"开箱即用 + 基础操作补全"**。基于 v1.0 实测反馈，补齐 6 项影响日常使用的体验缺口：会话房间管理、群成员可见性、设置页结构化、全局模型供应商注册表、Agent 创建后可编辑、文件树折叠修复与文件 CRUD。

目标判据：用户无需离开应用、无需"删了重建"、无需手动操作 Matrix 后台，即可完成完整的日常工作流。

## 2. M1 详细设计

### 2.1 会话列表 CRUD（①）

#### 现状
`RoomList.tsx` 纯只读；IM 层只有 `getRooms/send`。房间全靠 Matrix `/sync` 自动出现（创建 workspace 时自动建团队群）。

#### 行为定义

**新增房间**：用户点击房间列表顶部 `+`，弹出对话框：
- 房间名（必填）
- 类型：私聊（DM，单人对单）/ 群组（多对多）
- 私聊：选择一个对象（当前 workspace 内的其他真人用户或 agent bot）
- 群组：选择多个成员（可后续再加）

**重命名**：房间项右键/悬停 → `重命名` → 行内编辑或小对话框。需房间 power level 足够（创建者=管理员恒可）。

**解散/退出（自适应，核心设计）**：

Matrix 协议事实：**没有任何用户能"删除"房间**。房间在**最后一个成员离开**时才被 homeserver 清理消亡。因此"删除群"的语义必须根据成员构成自适应：

| 检测到的成员构成 | 按钮文案 | 实际行为 |
|---|---|---|
| 只有本地用户 + 本地 bot（v1.1 全部情况） | **解散群组** | 全部 bot `leaveRoom`（用各自 token）+ 用户最后离开 → 0 成员 → homeserver 清理 |
| 含其他真人/远程用户（v2+ federation 后才会出现） | **退出群组** | 仅用户（+其拥有的 bot）离开，房间保留 |

**实现关键 —— 远程成员检测**：v1.1 所有成员都在同一本地 homeserver，故现在恒为"解散"。检测逻辑用 userId 的 homeserver 域名：`userId.split(':')[1] === 本地 server_name` 即本地成员。v2 接入外部 homeserver/federation 后自动切换为"退出"。

**系统团队群保护**：创建 workspace 时自动建的团队群（`room.isSystem === true`）绑定该 workspace 的 agent 调度通道，**禁止单独解散**（会孤儿化 agent 协作），只能随 workspace 删除一起清掉。UI 上系统群不显示解散按钮，显示锁标记。

#### IPC（新增）

| IPC | 入参 | 返回 | 说明 |
|---|---|---|---|
| `im:createRoom` | `{ name: string; isDirect: boolean; inviteUserIds: string[] }` | `{ roomId: string }` | DM 设 `is_direct:true` + Preset.TrustedPrivateChat；群组 Preset.PrivateChat |
| `im:renameRoom` | `{ roomId: string; name: string }` | `{ ok: boolean }` | `client.setRoomName` |
| `im:dissolveRoom` | `{ roomId: string }` | `{ ok: boolean; dissolved: boolean }` | 自适应：`dissolved=true` 表示已清空消亡；系统群抛错 |

#### 数据流
1. 前端调 IPC → 后端用用户 Matrix client 执行（解散时额外用各 bot token 创建临时 client 让 bot 离开）
2. 操作完成 → 前端 `loadRooms()` 刷新
3. `/sync` 自动捕获成员变更，房间列表实时更新

#### 错误处理
- 无 power level 重命名 → 捕获 Matrix `M_FORBIDDEN`，提示"无权限"
- bot token 丢失（keychain 缺失）→ 解散降级为"退出"（用户离开，bot 残留但不影响用户），提示"部分 bot 凭证丢失，已退出但未完全解散"
- 网络断开 → 提示重试

### 2.2 群成员查看（②）

#### 现状
RoomList 不显示成员；无 `joined_members` 接口。

#### 行为定义
选中某房间后，IM 视图右侧（或可展开侧栏）显示成员列表：
- 头像 + 显示名
- 角色徽标：管理员（power level ≥ 50）/ 成员
- 身份徽标：🤖 bot / 👤 真人 / ⭐ 本地用户（你自己）
- 点击成员 →（v1.2）发起私聊；v1.1 仅展示

#### IPC（新增）

| IPC | 入参 | 返回 | 说明 |
|---|---|---|---|
| `im:getMembers` | `{ roomId: string }` | `{ members: RoomMember[] }` | `client.getJoinedRoomMembers` |

```ts
interface RoomMember {
  userId: string;
  displayName: string;
  avatarUrl: string | null;
  powerLevel: number;
  isBot: boolean;       // userId 匹配已注册 bot 列表
  isLocalUser: boolean; // 是否当前登录用户
}
```

#### 数据流
- `selectRoom` 时触发 `loadMembers(roomId)`，缓存到 `im.store`
- `/sync` 收到 membership 事件时增量更新成员列表

### 2.4 全局模型供应商注册表（④）—— v1.1 最大项

#### 现状
当前每个 agent 在"添加 agent"时独立填写 `provider + modelName + baseUrl + apiKey`。无全局注册表，重复填写、无法统一管理、改一处要逐个 agent 改。

#### 核心设计决策：注册表 = 表单填充器（COPY 模型）

**供应商注册表只是创建/编辑 agent 时的"快捷填充"工具，不是 agent 运行时的依赖源。**

- 创建/编辑 agent 时，从下拉选供应商 → 自动带出 `baseUrl` + 预填 `apiKey` + 预填 `defaultModel`
- 保存 agent 时，`baseUrl` 与 `apiKey` **复制**进 agent 定义 / agent 实例的 keychain 槽位（沿用现有 `model_base_url` 列 + `agent.<instanceId>.llm_api_key`）
- 删除/修改供应商**不影响已存在的 agent**（它们持有自己的副本）

理由：
1. agent 运行时自洽——删供应商不会让运行中的 agent 崩溃
2. 沿用现有数据模型，改动最小
3. 仍保留"使用自定义供应商"入口（一次性、不入注册表）

#### 数据模型（migration v10）

```sql
CREATE TABLE IF NOT EXISTS model_providers (
  id TEXT PRIMARY KEY NOT NULL,
  name TEXT NOT NULL UNIQUE,          -- 显示名 "GLM" / "DeepSeek"
  base_url TEXT NOT NULL,             -- https://open.bigmodel.cn/api/coding/paas/v4
  api_key_ref TEXT NOT NULL,          -- keychain key: provider.<id>.api_key
  default_model TEXT,                 -- 默认模型名 glm-5.2（创建 agent 时预填）
  is_default INTEGER NOT NULL DEFAULT 0,  -- 是否默认供应商（创建 agent 时预选）
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

**keychain**：apiKey 存于 `provider.<id>.api_key`，与现有 `keychain.ts`（SERVICE_NAME = 'Momo Studio'）一致。

#### IPC（新增）

| IPC | 入参 | 返回 | 说明 |
|---|---|---|---|
| `provider:list` | — | `ModelProvider[]`（不含 apiKey） | 列出全部供应商 |
| `provider:create` | `{ name; baseUrl; apiKey; defaultModel?; isDefault? }` | `ModelProvider` | 建 keychain + 插 DB；若 isDefault 置他者为 0 |
| `provider:update` | `{ id; name?; baseUrl?; apiKey?; defaultModel?; isDefault? }` | `ModelProvider` | apiKey 非空才更新 keychain |
| `provider:delete` | `{ id }` | `{ ok }` | 删 DB + 删 keychain；已存在 agent 不受影响（持副本） |
| `provider:setDefault` | `{ id }` | `{ ok }` | 排他置 isDefault |
| `provider:testConnection` | `{ baseUrl; apiKey; model }` | `{ ok; error? }` | 发最小 chat completion 验证连通 |

```ts
interface ModelProvider {
  id: string;
  name: string;
  baseUrl: string;
  defaultModel: string | null;
  isDefault: boolean;
  createdAt: string;
  // 注意：不返回 apiKey
}
```

#### 前端：设置 → 模型供应商

- 供应商列表（卡片/行）：名称、baseUrl、默认模型、⭐默认标记
- `+ 添加供应商` 按钮 → 对话框（名称、baseUrl、apiKey[password]、默认模型、设为默认 checkbox、"测试连接"按钮）
- 每项操作：✏️ 编辑 / 🗑 删除（确认）/ ⭐ 设为默认
- 预置 3 个常见供应商模板（GLM / DeepSeek / OpenAI）—— 仅作表单快捷模板，用户确认才入库

#### 前端：Agent 创建/编辑表单改造（与 ⑤ 协同）

`AddAgentDialog`（后改名 `AgentFormDialog`，支持 create/edit 双模式）模型字段区：
- **供应商**下拉（来自 `provider:list`，含"自定义…"选项）
  - 选已有供应商 → 自动填 baseUrl + apiKey(password) + 预填 modelName=defaultModel
  - 选"自定义…" → 退化到当前自由填写模式
- **模型名** 文本框（选供应商时预填，可改）
- apiKey 仍按现有流程在保存时复制到 agent 实例 keychain

## 3. M2 详细设计

### 3.1 Agent 创建后可编辑（⑤）

#### 现状
`createCustom` IPC 有，无 update；`AddAgentDialog` 仅创建态。改 prompt/model 必须删了重建（丢 bot 账号 + 历史）。

#### 定义 vs 分配的边界（关键澄清）

Agent 有两层：
- **AgentDefinition**（定义/模板）：name / slug / description / systemPrompt / modelProvider / modelName / modelBaseUrl / iconEmoji。**不含 apiKey**。
- **AgentAssignment**（实例）：绑定到某 workspace，有 instanceId + bot 账号 + apiKey（存 keychain）。

用户日常说的"一个 agent"通常是"定义 + 它在当前 workspace 的分配"。编辑功能改的是**定义层**。apiKey 不在定义层，故：

#### 行为定义
- AgentList 每项加 ✏️ 编辑按钮 → 打开 `AgentFormDialog`（edit 模式，预填现有 def）
- 可改字段（均为定义层）：name / description / systemPrompt / modelProvider / modelName / modelBaseUrl / iconEmoji
- **slug 只读**（身份标识，改它会断引用）
- **apiKey 不在编辑表单**：编辑定义不碰实例密钥。需改密钥的用户场景极少（密钥轮换）；v1.1 提供 AgentList 项上独立的"更新 API Key"小动作（弹框输入新 key → 写入实例 keychain 槽 `agent.<instanceId>.llm_api_key`），与编辑解耦
- 保存 → `agent:updateDefinition`

#### 运行中实例的处理（关键决策）

更新 def 会影响该 def 的所有 assignment。运行中的实例持有旧 prompt/model，不会自动热加载。决策：

**更新后自动停止受影响的运行中实例，并明确提示用户手动重启。**

理由：
- prompt/model 改了，旧 runtime 已过时，继续跑会产出与配置不一致的结果
- 不自动重启——可能打断进行中的任务；让用户掌握重启时机
- 用户在 AgentList 看到"已停止"状态 + 启动按钮（v1.0 已有），主动重启即应用新配置

UI 提示：保存成功后 toast："Agent 配置已更新。N 个运行中的实例已停止，请点击启动以应用新配置。"

#### IPC（新增）

| IPC | 入参 | 返回 | 说明 |
|---|---|---|---|
| `agent:updateDefinition` | `{ id; name?; description?; systemPrompt?; modelProvider?; modelName?; modelBaseUrl?; iconEmoji? }` | `AgentDefinition` | 更新 DB；找出该 def 所有运行中 assignment → 逐个 stop（不重启） |
| `agent:updateApiKey` | `{ instanceId; apiKey }` | `{ ok }` | 更新实例 keychain 槽；若运行中需重启才生效（提示用户） |

#### 数据流
1. 前端 `updateDefinition` → 后端 update DB row
2. 后端查 `agent_assignments WHERE agent_definition_id = id AND running`
3. 对每个运行中实例调现有 `stopRuntime(instanceId)`
4. 返回新 def → 前端刷新列表（实例显示"已停止"）

### 3.2 文件树折叠修复（⑥）

#### 现状核查
`FileTreeView` **已有折叠逻辑**（`toggleDir` / `expandedDirs`，根 `.` 默认展开）。用户报告"默认全展开、不能折叠"——疑似 bug 或体验问题，需复现定位，**不在设计阶段臆测根因**。

#### 候选假设（实现时用 systematic-debugging 验证）
- H1：根级目录无折叠开关（`FileTree` 直接渲染 `FileTreeView dirPath="."`，根本身无 ▶/▼ 按钮），用户感觉顶层无法收起
- H2：深层目录首次加载即展开（需核查是否某处批量 add expandedDirs）
- H3：折叠状态未持久化，切换 workspace 后重置

#### 设计（不论根因如何都要做）
- `FileTree` 顶部加工具条：🔄刷新 / ▼全部折叠（清空 expandedDirs 除根外）/ ➕新建（接 ⑦）
- 修复实际折叠 bug（实现期定位）
- 折叠状态可选持久化到 localStorage（按 workspaceId）—— v1.1 做，低成本提升

### 3.3 文件 CRUD（⑦）

#### 现状
IPC 只有 `read/write/list`，无 create/delete/rename/move。WorkspaceFS 仅读+写防御。

#### 行为定义

**新建**：工具条/右键 → `新建文件` / `新建文件夹` → 输入名 → 创建（文件可空内容）
**重命名**：右键 → `重命名` → 行内编辑名（同父目录内改名）
**删除**：右键 → `删除` → 确认（目录递归删除，提示"将删除 N 个文件"）
**移动**：右键 → `移动到…` → 文件夹选择对话框 → 移动；拖拽移动留 v1.2

#### Git 集成决策
**手动文件操作不自动 git commit。** 理由：
- git policy 是约束 agent 写操作的；用户手动操作应自由（scratch 文件等）
- 用户提交需求由后续"提交"按钮（v1.2）满足
- v1.1 只做 FS 操作 + 文件树刷新，保持范围紧凑

所有操作经 `WorkspaceFS` 路径校验（现有 `..` 越界 / 符号链接逃逸防御）。

#### IPC（新增）

| IPC | 入参 | 返回 | 说明 |
|---|---|---|---|
| `file:create` | `{ workspaceId; path; type: 'file'\|'dir'; content? }` | `{ ok }` | WorkspaceFS 校验 + 创建 |
| `file:delete` | `{ workspaceId; path }` | `{ ok }` | 文件或递归删目录 |
| `file:rename` | `{ workspaceId; oldPath; newName }` | `{ ok }` | 同父目录改名 |
| `file:move` | `{ workspaceId; srcPath; destDirPath }` | `{ ok }` | 移入目标目录 |

#### 数据流
1. 操作 → 后端 WorkspaceFS 执行 → 返回
2. 前端刷新受影响目录 `loadDir`（重命名/移动需刷新新旧父目录）
3. 若删除/移动的是当前打开文件 → 关闭编辑器 tab

## 6. 安全考量

| 风险 | 缓解 |
|---|---|
| 供应商 apiKey 明文落 DB | 仅存 `api_key_ref`（keychain 引用），明文在 keychain |
| 文件 CRUD 路径越界 | 全部经 WorkspaceFS 现有防御（`..` 拦截 / 符号链接逃逸拦截） |
| 递归删目录误删 | UI 强制确认 + 显示将删文件数；WorkspaceFS 限制在 workspace 根内 |
| 解散房间误操作 | 系统群禁删；普通群二次确认；bot token 缺失时降级为"退出"不静默失败 |
| Agent 编辑破坏运行中任务 | 不自动重启，仅停止 + 明确提示，用户掌控重启时机 |
