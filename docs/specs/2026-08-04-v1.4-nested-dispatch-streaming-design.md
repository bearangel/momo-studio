# v1.4 补充设计：多 Agent 委派嵌套流式展示

> 状态：草案
> 日期：2026-08-04
> 范围：v1.4 增量优化——解决 dispatch/task_reply 在流式场景下的三个 UX 问题

## 1. 痛点

v1.4 流式回复上线后，多 agent dispatch 场景暴露三个问题：

### 1.1 子 agent 内容重复

子 agent 既通过 IPC 流式推送完整回复（最终 Matrix 消息含 thinking + tool_calls），又发送 `task_reply(completed)` 事件。两条消息内容一致，renderer 渲染成两个独立消息。

### 1.2 dispatch 打断主对话流

dispatch 本质是 PM 在 chat loop 中调用的工具，但当前实现把它发成独立 Matrix 事件（DispatchCard），在 IM 中渲染为顶层消息。用户看到 PM 突然冒出一张调度卡片，打断了 PM ↔ 用户的对话连续性。

### 1.3 PM 最终回复与用户原始消息脱节

PM 收到用户消息后：分析 → dispatch → 等结果 → 写总结。中间产生 4-5 条独立消息（DispatchCard、in_progress、流式回复、completed、PM 总结），PM 的最终回复出现在时间线最底部，与用户的原始问题隔了多条消息，用户看不出对应关系。

### 1.4 并行委派无清晰展示

PM 可能在一轮中向多个子 agent 委派（LLM 返回多个 dispatch tool_calls）。当前实现下，多个 DispatchCard + TaskReplyCard 堆叠在时间线上，用户无法直观看出哪些任务在并行、各自进度如何。

## 2. 目标

把 dispatch/task_reply 从**独立顶层消息**降级为 PM 流式气泡内的**嵌套展示**：

- PM 的流式气泡是对用户消息的唯一回复入口
- dispatch 作为 PM 气泡内的工具调用 chip（明确显示委派给了谁）
- 子 agent 的工作过程嵌套在对应 dispatch chip 下方（可展开/折叠）
- 并行委派：多个 dispatch chip 纵向堆叠，各自独立状态
- 内容零重复

## 3. 核心概念

### 3.1 嵌套关联：parentStreamSessionId

每个子 agent 的流式 session 关联到父 agent（PM）的流式 session。renderer 据此嵌套渲染。

```
PM streamSessionId: "pm-uuid"
  └─ dispatch tool_call → subStreamSessionId: "sub-uuid-1"
       └─ sub agent start chunk: parentStreamSessionId: "pm-uuid"
  └─ dispatch tool_call → subStreamSessionId: "sub-uuid-2"
       └─ sub agent start chunk: parentStreamSessionId: "pm-uuid"
```

### 3.2 chip 状态自动管理

| 子 agent 状态 | chip 显示 | 嵌套区行为 |
|---|---|---|
| 排队等待 | 📤 名称 ⏳排队 | 不渲染 |
| 执行中 | 📤 名称 ⏳执行中 | **自动展开**（实时看进度） |
| 已完成 | 📤 名称 ✅完成 | **自动折叠**（点击展开查看） |
| 失败 | 📤 名称 ❌失败 | 保持展开（查看错误） |

### 3.3 不再独立渲染的消息类型

以下 Matrix 事件不再作为独立顶层消息渲染（仅在嵌套结构内体现）：

| 事件类型 | 原渲染方式 | 新处理 |
|---|---|---|
| `io.momo-studio.dispatch` | DispatchCard 顶层卡片 | 不独立渲染；信息内化到 PM 气泡的 dispatch chip |
| `io.momo-studio.task_reply` | TaskReplyCard 顶层卡片 | 不独立渲染；状态变化体现在 dispatch chip |
| 子 agent `m.room.message`（含 parent_stream_session_id） | 顶层气泡 | 嵌套到 PM 气泡的 dispatch chip 下 |

### 3.4 底部进度指示

PM 有多个 dispatch 在进行时，气泡底部显示进度：

```
⏳ 等待 2/3 子任务完成  [🐵✅] [🧪⏳] [📝⏳]
```

所有完成后消失，PM 继续流式输出最终总结。

## 4. StreamChunk 扩展

### 4.1 新增字段

在现有 `StreamChunk` 类型上扩展（向后兼容——新字段全部可选）：

```typescript
type StreamChunk =
  | { type: 'start'; streamSessionId: string; roomId: string; botUserId: string;
      /** v1.4 补充：父 agent 的 streamSessionId（子 agent 委派场景） */
      parentStreamSessionId?: string;
      /** v1.4 补充：子 agent 的展示名称（嵌套 chip 上显示） */
      subAgentName?: string;
      /** v1.4 补充：子 agent 的 emoji 头像 */
      subAgentAvatar?: string;
    }
  | { type: 'thinking'; streamSessionId: string; delta: string }
  | { type: 'text'; streamSessionId: string; delta: string }
  | { type: 'tool_call'; streamSessionId: string; toolName: string; args: Record<string, unknown>;
      /** v1.4 补充：dispatch 工具调用的子 stream session ID */
      isDispatch?: boolean;
      subStreamSessionId?: string;
      subAgentName?: string;
      subAgentAvatar?: string;
    }
  | { type: 'tool_result'; streamSessionId: string; toolName: string; result: string; success: boolean;
      /** v1.4 补充：dispatch 完成时的子 agent 状态摘要 */
      subStatus?: 'completed' | 'failed' | 'timeout';
    }
  | { type: 'end'; streamSessionId: string; finishReason: 'stop' | 'budget_exhausted' | 'interrupted' | 'error'; error?: string };
```

### 4.2 子 agent chunk 的关联规则

子 agent 的 `start` chunk 携带 `parentStreamSessionId`。renderer 收到后：
1. 在父 agent 的 StreamState 中查找对应的 dispatch tool_call（按 `subStreamSessionId` 匹配）
2. 创建子 StreamState，嵌套在父的 dispatch chip 下
3. 后续 thinking/text/tool_call/tool_result/end chunk 按 `streamSessionId` 更新子状态

## 5. Runtime 改造

### 5.1 PM 侧：dispatch 工具调用增强

PM 的 `runChatLoop` 执行 `dispatch:*` 工具时：

```
1. 生成 subStreamSessionId = randomUUID()
2. 发 tool_call chunk:
   { type:'tool_call', streamSessionId: PM_SESSION,
     toolName: 'dispatch:programmer', args: {task: "..."},
     isDispatch: true, subStreamSessionId, subAgentName: "研发工程师", subAgentAvatar: "🐵" }
3. 构建 dispatch 消息（Matrix 事件），额外携带 tool_stream_session_id 字段
4. 等待 task_reply
5. 收到 reply 后发 tool_result chunk:
   { type:'tool_result', streamSessionId: PM_SESSION,
     toolName: 'dispatch:programmer', result: reply.body, success: true,
     subStatus: reply.status === 'completed' ? 'completed' : 'failed' }
```

### 5.2 子 agent 侧：嵌套流式

子 agent 的 `runChatLoop` 检测到 dispatch 模式（从 dispatch 消息中读取 `tool_stream_session_id`）：

```
1. start chunk 携带 parentStreamSessionId = dispatch.tool_stream_session_id
2. 正常流式 thinking/text/tool_call/tool_result
3. **不发最终 m.room.message**——避免与 PM 的嵌套展示重复
   （改为：发一条带 parent_stream_session_id 的 m.room.message，renderer 嵌套渲染而非顶层）
4. task_reply 照常发送（PM 需要接收结果），但不再渲染为独立卡片
```

### 5.3 dispatch.ts 扩展

`DispatchContent` 新增：

```typescript
/** v1.4 补充：子 agent 流式 session ID，用于关联 PM 气泡内的嵌套展示 */
tool_stream_session_id?: string;
```

`buildDispatchMessage` 新增 `toolStreamSessionId` 可选参数。

### 5.4 并行 dispatch 处理

当 PM 的 LLM 在一轮中返回多个 dispatch tool_calls 时，当前代码已按顺序执行（for 循环）。每个 dispatch 独立生成 `subStreamSessionId`，renderer 纵向堆叠多个 chip。

未来如果支持真正的并行执行（Promise.all），chunk 的 `streamSessionId` 区分机制不变——每个子 agent 有独立 session，renderer 按 session 分别渲染。

## 6. UI 设计

### 6.1 PM 气泡结构（含嵌套）

```
AgentStreamBubble (PM)
├── ThinkingSection (PM 自己的 thinking)
├── PM 的工具调用 chips
│   ├── ✓ read_file
│   └── ✓ list_files
├── DispatchChip[] (dispatch 委派展示)
│   ├── 📤 🐵 研发工程师  ✅完成  ▾
│   │   └── [展开] SubAgentSection
│   │       ├── 💭 thinking
│   │       ├── ✓ read_file
│   │       ├── ✓ write_file
│   │       └── 正文
│   └── 📤 🧪 测试工程师  ⏳执行中  ▾
│       └── [展开] SubAgentSection
│           ├── 💭 thinking
│           └── ⏳ run_tests
├── 进度指示器（有未完成 dispatch 时）
│   └── ⏳ 等待 1/2 子任务完成
└── PM 正文（最终总结）
```

### 6.2 新组件：DispatchChip

```tsx
interface DispatchChipProps {
  subAgentName: string;
  subAgentAvatar: string;
  status: 'queued' | 'executing' | 'completed' | 'failed';
  subStream?: StreamState;  // 子 agent 的聚合状态
  taskSummary?: string;     // dispatch 时的任务描述摘要
}
```

渲染：
- 紧凑头行：`📤 [avatar] [name] [status_icon] [status_text] ▾/▸`
- 状态颜色：排队=#888, 执行中=#fbbf24, 完成=#4ade80, 失败=#f87171
- 点击切换展开/折叠
- 展开时渲染 SubAgentSection

### 6.3 新组件：SubAgentSection

复用 AgentStreamBubble 的内部结构（ThinkingSection + ToolCallChip + 正文），但：
- 嵌套在 DispatchChip 下方（缩进 + 左边框视觉关联）
- 不显示底部状态栏/停止按钮（由父 chip 管理）
- 不再嵌套 dispatch chip（暂不支持 3 级嵌套；如果子 agent 也 dispatch，其 dispatch chips 平铺在子 section 内，不继续缩进）

### 6.4 并行展示规则

- 每个 dispatch chip 独立一行，纵向堆叠
- 执行中的自动展开（用户实时看到进度）
- 完成后自动折叠（节省空间）
- 失败的保持展开（用户需查看错误）
- 用户手动展开/折叠覆盖自动行为

### 6.5 进度指示器

PM 气泡底部（正文之前），当有未完成的 dispatch 时显示：

```
⏳ 等待 2/3 子任务完成
```

计数：`已完成数 / 总 dispatch 数`。全部完成后消失。

### 6.6 消息过滤

MessageList / MessageBubble 渲染逻辑调整：

1. **`io.momo-studio.dispatch` 事件**：不渲染为独立 DispatchCard
2. **`io.momo-studio.task_reply` 事件**：不渲染为独立 TaskReplyCard
3. **子 agent `m.room.message`（含 `io.momo-studio.parent_stream_session_id`）**：不渲染为顶层气泡

这三类事件的信息已通过 PM 气泡的嵌套结构完整呈现，独立渲染会导致重复和混乱。

**注意**：非 dispatch 场景的 `task_reply`（如用户直接与子 agent 对话）仍正常渲染。

## 7. 持久化与历史还原

### 7.1 子 agent 最终消息

子 agent 在 dispatch 模式下仍发 `m.room.message`，但 content 包含：

```json
{
  "msgtype": "m.text",
  "body": "子 agent 的最终正文",
  "io.momo-studio.stream_session_id": "sub-uuid",
  "io.momo-studio.parent_stream_session_id": "pm-uuid",
  "io.momo-studio.thinking": "思考过程全文",
  "io.momo-studio.tool_calls": [...]
}
```

`parent_stream_session_id` 标记此消息应嵌套渲染。

### 7.2 PM 最终消息

PM 的最终 `m.room.message` 的 `io.momo-studio.tool_calls` 数组中，dispatch 类型的 tool call 包含额外字段：

```json
{
  "name": "dispatch:programmer",
  "args": {"task": "..."},
  "result": "task_reply body",
  "success": true,
  "isDispatch": true,
  "subStreamSessionId": "sub-uuid",
  "subAgentName": "研发工程师",
  "subAgentAvatar": "🐵"
}
```

### 7.3 历史加载时嵌套还原

renderer 加载 Matrix 历史时：

1. 遍历消息列表
2. PM 的 m.room.message（含 `io.momo-studio.tool_calls`）→ 渲染为增强气泡
3. dispatch tool call → 渲染为 DispatchChip（从 tool_calls 数组的 `isDispatch` 字段识别）
4. 查找 `io.momo-studio.parent_stream_session_id === subStreamSessionId` 的消息 → 嵌套到对应 DispatchChip 下
5. `io.momo-studio.dispatch` / `io.momo-studio.task_reply` 事件 → 跳过（不独立渲染）

## 8. 错误处理

| 场景 | 处理 | 用户可见 |
|---|---|---|
| 子 agent 执行失败 | task_reply(failed) → dispatch chip 状态 ❌失败 → PM 可能在总结中说明 | chip 展开显示错误信息 |
| 子 agent 超时 | dispatch 超时 → chip 状态 ❌超时 | chip 显示「⏱ 超时」 |
| 子 agent 进程崩溃 | 主进程发 end(error) → chip 状态 ❌失败 | chip 显示「进程异常退出」 |
| PM 在等待 dispatch 时被用户中断 | abort → PM chat loop 停止 → 子 agent 也应被中止 | PM 气泡标注「已中断」，chip 标注对应状态 |

### 8.1 中断传播

当 PM 被 abort 时，正在执行的 dispatch 也需要中止：
- 主进程收到 PM 的 abort → 查找 PM 的 activeStreams 中所有子 agent session → 向子 agent 子进程发 abort
- 子 agent 收到 abort → 停止 → 发 end(interrupted)

主进程需要维护 parent→children 映射（在 start chunk 时记录）。

## 9. 向后兼容

- **无 dispatch 的对话**：行为完全不变（v1.4 的流式展示正常工作）
- **旧版 Matrix 消息**（无 parent_stream_session_id）：正常渲染为顶层气泡
- **StreamChunk 新字段**：全部可选，旧 chunk 不携带时按原有逻辑处理
- **dispatch.ts 新字段**：可选，旧版子进程不携带时 PM 正常工作
- **MessageBubble 历史**：无 isDispatch 的 tool_calls 按普通工具调用渲染

## 11. 实施顺序

1. StreamChunk 类型扩展 + dispatch.ts 加 tool_stream_session_id
2. Runtime：PM dispatch 增强（tool_call chunk + dispatch 消息）+ 子 agent 嵌套（start chunk parentStreamSessionId + m.room.message parent 字段）
3. Stream Store：parentStreamSessionId 关联 + 嵌套 StreamState
4. DispatchChip + SubAgentSection 组件
5. AgentStreamBubble 集成 dispatch chips + 进度指示器
6. MessageList 消息过滤（dispatch/task_reply/parent_stream 不独立渲染）
7. MessageBubble 历史还原（dispatch tool_calls → DispatchChip + 子消息嵌套）
8. 中断传播（PM abort → 子 agent abort）

## 12. 不在本次范围

- 3 级嵌套（子 agent 的子 agent）——v2
- 真正并行 dispatch 执行（Promise.all）——当前顺序执行已满足需求
- 非 team room 的 dispatch 展示——dispatch 仅在 team room 发生
