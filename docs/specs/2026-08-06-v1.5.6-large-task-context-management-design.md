# v1.5.6 — 大任务上下文管理优化

**版本**：v1.5.6
**作者**：Sisyphus
**日期**：2026-08-06
**状态**：已实施

## 1. 背景

v1.5.5 解决了 PDU 截断丢失 dispatches + sendEvent 失败死循环的紧急 bug，但用户进一步问"如何支持全代码 review / 超大模块连续编写"场景。对比 opencode/Claude Code 后发现两个核心差距：

1. **read_file 一次性返回整个文件**：LLM 调一次 read_file 就把整个大文件塞进 LLM 上下文，多次累积爆模型上下文上限
2. **长回复无分段机制**：LLM 单次回复超 ~3KB 就有 PDU 截断风险，长任务（review 报告 / 模块说明）必然触发 fitEventContent 4-5 级截断丢失元数据

## 2. 目标

- 让 read_file 支持分页读，避免 LLM 上下文爆炸
- 让 LLM 主动分段持久化回复，避免 PDU 截断

## 3. 非目标

- 持久化分层（thinking/tool_calls 搬到 SQLite）→ 留 v1.5.7
- LLM 主动 compact 上下文 → 留 v1.5.7
- PM 自动 dispatch 拆任务 → 留 v1.6

## 4. 实施

### 4.1 read_file 分页（file-tools.ts）

**新参数**：
- `offset`（可选）：起始行号（1-based），默认 1
- `limit`（可选）：本次返回最大行数，默认 2000

**实现**：
1. `wsFs.readFile` 读全文
2. `split('\n')` → `slice(offset-1, offset-1+limit)`
3. 还有更多行 → 尾部追加 `\n...(共 N 行，已显示 M-K 行；用 offset=K+1 继续读取)`
4. 已是末尾但本次分页 → 追加 `\n（文件末尾，共 N 行）`

**约束**：
- `limit` 上限 5000（防 LLM 误传巨大值撑爆 LLM 上下文）
- `offset` 超出文件总行数 → 返回 `(空) 文件共 N 行，offset=X 超出范围`
- 向后兼容：小文件无分页参数 → 完整返回（与 v1.5.5 行为一致）

**测试**：6 用例
- 小段分页
- 默认 2000 行触发提示
- offset 超界
- 读到末尾标记
- limit 上限保护
- 完整读小文件无分页提示

### 4.2 task_complete 主动分段（runtime-entry.ts）

**工具定义**：
```typescript
{
  name: 'task_complete',
  description: '完成本段回复并持久化为一条消息。当回复内容超过约 3KB 或完成阶段性子任务时调用...',
  inputSchema: {
    properties: {
      summary: { type: 'string', description: '本段内容（写入 Matrix 消息 body）' },
      nextStep: { type: 'string', description: '下一段要做什么（提示自己继续；可选）' },
    },
    required: ['summary'],
  },
}
```

**执行逻辑**（chat loop 内联，不走 ToolModule 路径）：
1. 收到 `tc.name === 'task_complete'` → 增加 segmentCount
2. 检查 `segmentCount > MAX_TASK_SEGMENTS` → 强制结束 chat loop（防无限分段）
3. 持久化当前段：
   - 段 sessionId = `${streamSessionId}#seg${segmentCount}`（避免与最终消息冲突）
   - body = `summary || accumulatedText.trim() || '(空段)'`
   - `io.momo-studio.segment_index` / `segment_of` 元数据
4. 重置 `accumulatedText = ''` + `accumulatedThinking = ''`
5. 推 stream chunk（tool_call + tool_result）让 renderer 知道分段
6. 推 messages：assistant（summary + toolCalls）+ tool（result 提示继续）
7. `toolCallCount++` / `budgetRemaining--`
8. `continue`（chat loop 不退出，下一轮 LLM 继续生成新段）

**约束**：
- `MAX_TASK_SEGMENTS = 5`（防 LLM 误用；5 段 × 5KB = 25KB 足够典型长任务）
- 分段失败（sendEvent 抛错）不致命——LLM 仍能继续工作，只是这一段没持久化

## 5. 关键设计决策

### 5.1 read_file 默认 2000 行

跟 opencode 标准对齐。典型 LLM 上下文 8K-32K tokens，2000 行代码约 5K-15K tokens，留充足预算给 thinking + 其他工具结果。

### 5.2 task_complete 不走 ToolModule

虽然名字像工具，但语义是"chat loop 控制流"——它需要访问 + 修改 chat loop 内部状态（accumulatedText / segmentCount / messages），这无法通过 ToolContext 暴露。内联处理最简洁。

### 5.3 分段 session id 加 `#segN` 后缀

renderer 的 stream store 按 streamSessionId 索引 StreamState。如果分段消息用相同 sessionId，会和最终消息混淆（覆盖 / 错误拼接）。`#segN` 后缀让分段消息独立渲染为多条 MessageBubble（按时间顺序排列），符合"分段流式输出"的视觉预期。

### 5.4 重置 accumulatedText 而非累积

LLM 调 task_complete 表示"这段完了"。下一段应该从头开始累积。如果不重置，下一轮 LLM 输出会拼到旧 accumulatedText 后面，导致 sendFinalMessage（最终消息）body 比预期长 5x。

### 5.5 nextStep 注入 tool_result

LLM 下一轮看到 tool_result "下一步：${nextStep}"，明确知道衔接点。比纯 systemPrompt 教学更直接。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 不主动调 task_complete（一直等到 PDU 截断） | systemPrompt 教学："输出超过约 3KB 时主动调 task_complete 分段" |
| LLM 滥用 task_complete（每段都调） | MAX_TASK_SEGMENTS=5 上限 |
| 分段消息渲染顺序错乱 | session id `#segN` + Matrix 时间戳天然保序 |
| 分段持久化失败 | 不抛错（warning log），LLM 继续，最坏丢失这一段（不致死循环） |
| read_file 误传 offset=0 / 负数 | 默认值兜底（offset=1） |
