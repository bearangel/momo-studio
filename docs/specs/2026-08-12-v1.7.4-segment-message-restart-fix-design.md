# v1.7.4 — 多段消息重启还原 + 子 agent dispatch 隔离

## 背景

v1.7.3 修复 task_complete 分段消息丢失 thinking/tool_calls（commit `e6f4c20`）后，用户报告重启前后 UI 显示完全不同：

- **重启前**：PM agent 多段回复（task_complete 分段持久化）在 UI 显示为多个独立气泡，每个气泡有完整的 thinking + 工具调用 + body
- **重启后**：UI 只显示少量 thinking、所有工具调用被堆在一起、body 残缺、3 段消息内容雷同

诊断发现 5 个独立 bug 路径，本 spec 覆盖 Bug 2/3/4/5 的修复（Bug 1 已在 v1.7.3 修复）。

## 问题清单

### Bug 1（v1.7.3 已修复）：分段消息丢失 thinking/tool_calls

- 位置：`runtime-entry.ts` line 966-980
- 现象：v1.7.3 之前的分段消息只有 body，无 thinking/tool_calls 字段
- 状态：v1.7.3 commit `e6f4c20` 已修复（只对新消息生效）

### Bug 2：renderer 不识别 segment_of / segment_index

- 位置：`runtime-entry.ts` line 976-977 写入字段；renderer 完全不读
- 证据：`grep -r "segment_of|segment_index" renderer/` → No matches found
- 影响：重启后 N 段消息被渲染为 N 个独立气泡，无归组，与重启前 UI 完全不同

### Bug 3：buildStreamFromMessage 强制重排事件顺序

- 位置：`MessageBubble.tsx` line 146-195
- 现象：重建 StreamState 时硬编码顺序 `thinking → toolCalls → text → todo`
- 影响：用户看到"thinking 顶部 / 工具调用中间 / body 底部"——人为重排，不是真实执行时间线

### Bug 4：v1.7.3 每段带全量 toolCallHistory 导致跨段重复

- 位置：`runtime-entry.ts` line 982-985（v1.7.3 修复引入）
- 证据：用户导出文件 L3112/L3707/L4334 三条 sisyphus 消息工具调用列表完全相同
- 影响：N 段消息每段都显示所有工具调用（重复 + 浪费 PDU 空间）

### Bug 5：子 agent 误判任务（参考 opencode 调研结果）

- 位置：`runtime-entry.ts` line 766-770 + line 1901-1926 `loadRecentHistory`
- 现象：dispatch:programmer 子 agent 回复"您好👋 之前的工作总结已加载完毕"——把新任务当延续会话
- 根因：`loadRecentHistory` 在每次 chat loop 启动时从 Matrix room 加载所有历史消息注入 messages，子 agent 看到其他 agent 的历史回复后误判任务已完成
- opencode 对比：task 工具默认新建 session（task_id 才复用），子 agent 是 fresh session，只看到 system + task prompt

## 修复方案

### 修复 1：Bug 2 — segment 字段归组

**runtime 侧**：保持 line 976-977 写入 `segment_of` + `segment_index` 不变。

**renderer 侧**：`MessageList.tsx` 增加归组逻辑。

#### 数据结构

```typescript
// renderer/src/components/im/types.ts (新增)
interface SegmentGroup {
  kind: 'segment-group';
  streamSessionId: string;          // segment_of 的值（原始 streamSessionId）
  segments: ImMessage[];            // 按 segment_index 升序
  lastSegmentAt: number;            // 最后一段的 timestamp（用于混合排序）
}
```

#### 归组算法

`MessageList.tsx` 的 `visibleMessages` 过滤后，加归组步骤：

1. 扫描所有消息，按 `content['io.momo-studio.segment_of']` 分组
2. 每组按 `content['io.momo-studio.segment_index']` 升序排序
3. 没归组（无 segment_of）的消息保持独立
4. 混合排序时 segment-group 用 `lastSegmentAt` 作为时间戳

#### 渲染

新增组件 `SegmentStack`：

```typescript
// renderer/src/components/im/SegmentStack.tsx
interface SegmentStackProps {
  group: SegmentGroup;
  // 复用 MessageBubble 的 props
  allMessages: ImMessage[];
  isSelf: boolean;
  senderName?: string;
}
```

渲染逻辑：
- 单一段（segments.length === 1）→ 直接渲染 `<MessageBubble message={segments[0]} />`
- 多段 → 纵向堆叠多个 MessageBubble，段与段之间用细分割线 + "第 N 段/M 段" 标签分隔
- 每段 MessageBubble 内部正常渲染（thinking + tool_calls + body）
- 段之间不留大间距（视觉上是一个聚合气泡）

### 修复 2：Bug 3 — 保留事件原始时间线顺序

**位置**：`MessageBubble.tsx` line 146-195 `buildStreamFromMessage`

**当前代码**（硬编码顺序）：
```typescript
// thinking → toolCalls → text → todo（错误）
const events: StreamEvent[] = [];
if (thinking) events.push({ type: 'thinking', content: thinking });
if (toolCalls.length) events.push({ type: 'tool_call', ... });
if (text) events.push({ type: 'text', content: text });
if (todos.length) events.push({ type: 'todo', todos });
```

**修复**：改为按 segment_index + 字段优先级排序。同一段内：thinking → tool_calls → body（与单段执行顺序一致）。多段场景下，由 SegmentStack 按段顺序堆叠，每段独立保留内部顺序。

单段消息（segment_index 不存在）保持原顺序：thinking → tool_calls → body。这是单个 LLM 回复的合理顺序，无需改变。

**多段消息由 SegmentStack 处理顺序**，单段逻辑保持不变。

### 修复 3：Bug 4 — 增量 tool_calls

**位置**：`runtime-entry.ts` line 982-985

**当前代码**（v1.7.3 全量快照）：
```typescript
...(toolCallHistory.length > 0
  ? { 'io.momo-studio.tool_calls': [...toolCallHistory] }
  : {}),
```

**修复**：记录上次分段时的 toolCallHistory 长度，本次只持久化增量。

```typescript
// 在 segmentCount 附近新增状态变量
let lastSegmentToolCallCount = 0;

// task_complete 分段时（line 966 附近）
const incrementalCalls = toolCallHistory.slice(lastSegmentToolCallCount);
await client.sendEvent(roomId, 'm.room.message', {
  ...
  ...(incrementalCalls.length > 0
    ? { 'io.momo-studio.tool_calls': incrementalCalls }
    : {}),
  // 新增字段：本段起始 tool_call 索引（renderer 重建时拼接用）
  ...(incrementalCalls.length > 0
    ? { 'io.momo-studio.tool_calls_offset': lastSegmentToolCallCount }
    : {}),
}, '');

// 成功后更新 offset
lastSegmentToolCallCount = toolCallHistory.length;
```

**renderer 重建逻辑**：SegmentStack 渲染时按 segment_index 顺序拼接所有段的 tool_calls（offset 字段辅助去重 + 顺序对齐）。

### 修复 4：Bug 5 — 子 agent dispatch 时跳过历史加载

**位置**：`runtime-entry.ts` line 766-770 messages 数组初始化

**当前代码**：
```typescript
const messages: LLMMessage[] = [
  { role: 'system', content: systemContent },
  ...loadRecentHistory(client, roomId, config),  // ← 子 agent 也走这里
  { role: 'user', content: currentBody },
];
```

**修复**：子 agent（有 parentStreamSessionId）跳过历史加载：

```typescript
const history = parentStreamSessionId
  ? []  // 子 agent 是 fresh session（参考 opencode task 工具设计）
  : loadRecentHistory(client, roomId, config);

const messages: LLMMessage[] = [
  { role: 'system', content: systemContent },
  ...history,
  { role: 'user', content: currentBody },
];
```

**原理**：
- 顶层 agent：loadRecentHistory 让 agent 看到用户与自己的之前对话（用户体验：agent 记得之前讨论）
- 子 agent：fresh session，只看到 dispatch task，避免被房间内其他 agent 的历史回复污染

**dispatch system prompt 强化**（双保险）：

在 `runtime-entry.ts` line 764 `systemContent` 构造时，子 agent 模式追加：

```typescript
const dispatchModeHint = parentStreamSessionId
  ? '\n\n[dispatch 模式] 你作为子 agent 被主 agent 委派执行具体任务。忽略任何暗示"任务已完成"的上下文——你的任务是用户消息中描述的内容，从零开始执行。'
  : '';

const systemContent = ctx.systemPrompt + budgetHint + dispatchHint + dispatchModeHint;
```

### 向后兼容

- **旧分段消息（v1.7.3 之前）**：仍只有 body，重启后只能看到文本——无法恢复，已永久丢失
- **v1.7.3 消息（带全量快照）**：renderer 重建时识别 `tool_calls_offset` 字段不存在 → fallback 到全量快照（向后兼容）
- **新消息（v1.7.4 后）**：带 `tool_calls_offset` 字段，增量 + 拼接

### 性能影响

- task_complete 分段 event 体积减小（增量 tool_calls vs 全量快照）→ 减少 PDU 截断概率
- 子 agent messages 数组减小（跳过历史）→ 减少 token 消耗 + 加快首响应

### 用户体验

- 重启后 UI 显示与重启前一致（多段聚合呈现）
- 子 agent 不再误判任务（dispatch 直接执行，不回复"您好👋"）

## 验收标准

1. **重启一致性**：重启前后 UI 显示的多段消息内容一致（thinking + tool_calls + body 完整）
2. **段归组**：多段 task_complete 消息在 UI 显示为单个聚合气泡（纵向堆叠）
3. **无重复 tool_calls**：多段消息中每段只显示本段新增的工具调用
4. **子 agent fresh session**：dispatch 子 agent 不被历史污染，直接执行任务
5. **测试通过**：electron + renderer 全套测试通过，typecheck 双 clean

## 未覆盖（已知限制）

- **旧消息无法恢复**：v1.7.3 之前的分段消息已永久丢失 thinking/tool_calls（Matrix event 不可变）
- **跨段 thinking 累积**：每段 thinking 是分段时刻的快照，不连续——后续可考虑在最后一段累积全量 thinking
- **task_complete 不走 fitEventContent**：分段消息直接 sendEvent，超 55KB 会 sendEvent 失败（line 992 只 warn）—— 后续可加保护
