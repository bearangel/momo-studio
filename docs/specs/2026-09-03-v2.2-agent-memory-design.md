# v2.2 Agent 记忆系统设计（三层记忆）

- 日期：2026-09-03
- 状态：已评审（三节逐节确认）
- 上游依赖：v2.0.0 平台架构（`2026-08-23-v2.0.0-platform-refactor-design.md`）、v25 agent 域设计（`2026-08-31-agent-team-session-redesign.md`）
- 调研底座：主流 AI agent 记忆系统调研 + 本地检索技术选型调研（完整报告与引用清单见 `.omo/ulw-research/20260903-094828/`，含 35+ 引用与 8 条代码级验证）

## 1. 背景与目标

Momo Studio 目前 agent 的上下文由 `MemoryProvider`（v1 实现：`SQLiteMemoryProvider`）提供，仅包含「最近 N 条消息截取 + 任务事件摘要」，跨会话/跨任务无记忆延续。v2.2 引入三层记忆系统：

- **会话记忆**（session scope）：会话滚动摘要 + 会话内关键决策，生命周期 = 会话生命周期
- **工作空间记忆**（workspace scope）：项目规范、架构决策、领域知识、经验教训，该 workspace 全部 agent 共享
- **全局记忆**（global scope）：用户偏好、通用约定，全平台共享

### 1.1 需求结论（已与产品负责人逐项确认）

| 需求点 | 结论 |
|---|---|
| 核心用途 | 四类全要：任务连续性、用户个性化、知识沉淀、长会话压缩 |
| 写入机制 | 混合：自动提取 + agent 工具 + 用户手动管理 |
| 共享语义 | 三层均团队共享（无 agent 私有维度；同一层内所有 agent 共享） |
| LAN 分享 | 不纳入 v2.0 LAN P2P 资源分享体系（本机隐私数据），schema 预留导出能力 |
| 记忆类型 | 常驻注入型（rule/preference）与检索型（knowledge/summary）双类型 |

### 1.2 典型场景

1. 用户在设置页向某 workspace 写入「研发规范」→ 该 workspace 所有 agent 下一条消息即遵守（常驻注入，无需检索）
2. 长会话关闭数日后重开 → agent 通过会话摘要接续上下文继续工作
3. agent 在会话中调 `memory_save` 记录关键架构决策 → 后续新任务可 `memory_search` 检索复用
4. 会话结束 → 自动提取管线沉淀用户偏好与新知识，用户在 UI 中复核（人是最終过滤器）

## 2. 行业调研摘要（选型依据）

1. **2025-2026 生产默认是「结构化文本为真相源 + 轻量派生索引」**：Claude Code / Manus / OpenClaw 等高流量平台以文本条目/文件为记忆本体，向量只是可选加速层；纯向量方案在数千条以上召回退化非线性且不可调试。
2. **三层架构已是收敛形态**：Claude（全局 CLAUDE.md + 项目级 + 会话）、VS Code Memory Tool（user/repo/session 三 scope、单条 200 行硬上限、拒绝越界写入）与本设计三层同构。
3. **常驻记忆注入预算生产共识 2,000–3,000 token**（8+ 独立来源交叉验证）。
4. **中文是全部主流开源方案的 BM25 盲区**（Mem0/Letta/LangGraph/Graphiti 对中文开箱零召回）；修复模式统一为 jieba 预分词 + FTS5。
5. **混合 BM25+向量（RRF）实证增益仅 ~1 NDCG 点**（0.698→0.707），<50k 短笔记场景不值得起步引入。
6. **写入主流是混合式**：ChatGPT（自动+用户管理）、Claude/Letta（agent 自编辑工具）、Mem0（事后提取管线，代码验证为 ADD-only）。

## 3. 技术选型

### 3.1 候选对比

| 方案 | 描述 | 结论 |
|---|---|---|
| **A（选定）** | SQLite `memories` 表为真相源 + FTS5/jieba BM25 检索，向量预留升级位 | 零新增 native 模块；与 sessions 内核同库；中文质量对齐工业实践；1–2 天落地检索层 |
| B | A + sqlite-vec + 本地 embedding（RRF 混合）一步到位 | pre-v1 扩展 + Electron ASAR 已知 bug + Linux aarch64 历史 ELF32 错件 + Win ARM64 无官方 prebuild + 100–600MB 常驻 RAM；实证增益用户无感 |
| C | 纯 Markdown 文件（Claude Code 风格 MEMORY.md） | 多 runtime 子进程并发写冲突风险；三层 scope 过滤/自动提取/UI 管理都要在文件层重新发明；md 不可查询最终仍需建索引 |

### 3.2 选定理由

架构铁律（单进程、零外部依赖、better-sqlite3 中心化）× 行业收敛方向 × 中文刚需（FTS5+jieba）× 实证收益比，四条线索全部指向方案 A。向量检索通过 schema 预留位变成「数据证明 BM25 召回不足时再加」的可逆决策。

关键技术事实：

- better-sqlite3 默认编译开启 FTS5（`SQLITE_ENABLE_FTS5`），无需任何新增依赖
- `@node-rs/jieba` 为 NAPI-RS prebuilt（约 11MB），Electron 主进程与子进程通用，无 node-gyp/ABI 问题
- FTS5 unicode61 对中文按字切分导致 BM25 无意义——必须写入/查询两侧同源 jieba 预分词

```
        │  IPC 命名空间 memory:*（renderer/src/ipc/types.d.ts 与 electron 双端契约）
─────────┼──────────────────────────────────────────────────────
主进程    ▼
├─ storage/memories/repo.ts        CRUD + FTS5 应用层双写（同事务）
├─ storage/memories/search.ts      BM25 检索（jieba 同源分词）
├─ storage/memories/tokenize.ts    jieba 分词共享模块（写入侧/查询侧唯一实现）
├─ memory/（升级既有模块）
│   ├─ types.ts                    扩展 MemoryEntry / PinnedMemoryView 等类型
│   ├─ injection.ts                常驻预算裁剪 + memoryHint 格式化
│   ├─ extraction.ts               自动提取管线（复用 session-naming 的主进程 LLM 模式）
│   ├─ sqlite-provider.ts          MemoryProvider 扩展实现
│   └─ index.ts                    singleton（既有测试注入器不变）
└─ agent/tools/memory-tools.ts     MemoryTools ToolModule（memory_* 三工具）
        │  WAL 共库（每进程独立连接，既有模式；主进程与 runtime 子进程并发读写）
─────────┼──────────────────────────────────────────────────────

```

不新建服务进程、不新增 native 模块、不改 IPC 总线架构。多进程并发写依赖既有 WAL + 短事务模式，注入每轮现拉保证最终一致。

## 5. 数据模型

### 5.1 memories 表（migration 027，内联 SQL 惯例；当前库最新迁移为 v26）

```sql
CREATE TABLE memories (
  id            TEXT PRIMARY KEY,              -- UUID
  scope         TEXT NOT NULL,                 -- 'global' | 'workspace' | 'session'
  workspace_id  TEXT,                          -- workspace/session 层非空；FK workspaces
  session_id    TEXT,                          -- session 层非空；FK sessions ON DELETE CASCADE
  kind          TEXT NOT NULL,                 -- 'rule' | 'preference' | 'knowledge' | 'summary'
  pinned        INTEGER NOT NULL DEFAULT 0,    -- 1=常驻注入（rule/preference 默认 1）
  content       TEXT NOT NULL,     -- 长度上限 2000 字符（rule 放宽至 4000）；不设下限（短偏好如「回答用中文」有效）
  tags          TEXT NOT NULL DEFAULT '[]',    -- JSON 字符串数组
  source        TEXT NOT NULL,                 -- 'user' | 'agent' | 'auto'
  source_detail TEXT,                          -- agent 名 / 提取批次 id（审计）
  confidence    REAL NOT NULL DEFAULT 1.0,     -- auto 条目默认 0.7
  use_count     INTEGER NOT NULL DEFAULT 0,    -- 检索/注入命中计数（遗忘策略依据）
  last_used_at  INTEGER,                       -- 最近命中时间（遗忘策略依据）
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  CHECK (scope IN ('global','workspace','session')),
  CHECK ((scope='global'     AND workspace_id IS NULL     AND session_id IS NULL)
      OR (scope='workspace'  AND workspace_id IS NOT NULL AND session_id IS NULL)
      OR (scope='session'    AND workspace_id IS NOT NULL AND session_id IS NOT NULL)),
  CHECK (kind IN ('rule','preference','knowledge','summary')),
  CHECK (source IN ('user','agent','auto')),
  FOREIGN KEY (workspace_id) REFERENCES workspaces(id),
  FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
CREATE INDEX idx_memories_ws      ON memories(workspace_id) WHERE scope IN ('workspace','session');
CREATE INDEX idx_memories_session ON memories(session_id)   WHERE scope='session';
CREATE INDEX idx_memories_pinned  ON memories(scope, workspace_id) WHERE pinned=1;
```

设计取舍：

- **scope 用列而非三张表**：同一套 CRUD/检索/注入代码，`WHERE` 过滤即分层
- **session 级联删除**：会话记忆生命周期 = 会话生命周期（会话解散自动清理）
- **pinned 独立于 kind**：用户可将任何条目置顶为常驻；默认 rule/preference 置顶、knowledge/summary 检索
- **source 决定主权**：`user` 条目 agent 工具只读；`agent`/`auto` 条目 agent 可管理；用户在 UI 对一切来源最高权
- **kind='summary' 与 session_summaries 表的分工**：`session_summaries` 存当前会话的滚动全文摘要（注入用，随会话删除）；`kind='summary'` 记忆条目是提取管线沉淀的「任务/阶段要点」（如任务完成要点写入 session 层、跨任务有价值的经验写入 workspace 层），走检索路径

### 5.2 session_summaries 表（长会话压缩）

```sql
CREATE TABLE session_summaries (
  session_id    TEXT PRIMARY KEY REFERENCES sessions(id) ON DELETE CASCADE,
  summary       TEXT NOT NULL,     -- 滚动总结全文（覆盖式更新）
  covered_until INTEGER NOT NULL,  -- 已覆盖消息 created_at 上界（增量压缩游标）
  updated_at    INTEGER NOT NULL
);
```

### 5.3 FTS5 派生索引

```sql
CREATE VIRTUAL TABLE memories_fts USING fts5(
  content, tags,
  content='memories', content_rowid='rowid',
  tokenize='unicode61'
);
```

两个关键工程决策：

1. **应用层双写而非触发器**：repo 的 insert/update/delete 在同一事务内同步写 FTS 表。跟随项目「表只经 repo 写」惯例，规避「任何进程任何裸 SQL 写入都要求已注册 SQL scalar function」的多进程陷阱（主进程 + 多个 warm runtime 子进程均写库）。
2. **jieba 分词在 TS 层而非 SQL function**：`storage/memories/tokenize.ts` 提供 `tokenizeForIndex(text): string`（jieba 切分后空格连接）作为唯一实现——写入侧把分词产物存入 FTS 表 content 列；查询侧用同一函数生成 MATCH 表达式（每 token 双引号包裹、AND 连接）。同源性由共享模块 + 契约测试锁死（见 §11.3）。

### 5.4 向量升级位（不在 v2.2 实施）

预留伴生表草案：`memory_embeddings(memory_id TEXT REFERENCES memories(id) ON DELETE CASCADE, dim INTEGER, vector BLOB, model TEXT)`。未来引入 sqlite-vec + 本地 embedding 时创建，`memories` 主表零迁移。升级触发条件：BM25 召回不足被真实使用数据证明（设置页可观测「检索未命中」反馈）。

## 6. 记忆流

### 6.1 三条写入路径（单一落库入口）

| 路径 | 入口 | 落库形态 | 生效时机 |
|---|---|---|---|
| ① 用户手动 | 设置→记忆页 新增/编辑 | `source='user'`，任意层/kind，可置顶 | 下一条消息（注入每轮现拉） |
| ② Agent 工具 | 会话中 `memory_*` 工具 | `source='agent'`，source_detail=agent 名 | 同上 |
| ③ 自动提取 | 提取管线（§6.4） | `source='auto'`，confidence=0.7，默认检索型 | 同上 |

所有写入统一走 `saveMemory`（repo 层事务：主表 + FTS 双写），单一写路径保证索引永不漂移。

### 6.2 Agent 工具（MemoryTools ToolModule）

```typescript
memory_save({ kind, content, tags?, scope? })   // scope 缺省 'workspace'；session 层仅会话成员可写
memory_search({ query, scope?, limit? })         // BM25 top-N（缺省 10）：id/kind/score/前 120 字
memory_forget({ id })                            // 仅 source='agent'|'auto' 可删；user 条目返回错误说明
```

- 工具定义在 `tools/memory-tools.ts` 实现 `ToolModule`，并在 `buildRuntimeContext` 动态工具白名单合并处登记（v1.7.1 教训：不进 `allowedTools` 会被 permission 层拒绝）
- 每次调用走既有 `logToolCall` 审计；`memory_search` 命中条目 `use_count+1`、`last_used_at` 更新
- agent 可通过定义 `deniedTools` 禁用（与 bash 等工具同级权限管理）
- **不给 `memory_update`**（v2.2 取舍）：更新 = 删旧 + 存新两步，规避改坏用户条目的边界判定复杂化；v2.3 依使用数据再议

### 6.3 注入策略（runChatLoop 唯一侵入点）

```typescript
// runtime-entry.ts runChatLoop 内，与既有 hint 同位拼接：
const memoryHint = await memory.getPinnedContext({
  workspaceId: config.workspaceId,
  sessionId: parentStreamSessionId ? null : roomId,  // 子 agent fresh：不带 session 记忆
});
const finalSystemContent = ctx.systemPrompt + budgetHint + dispatchHint + taskHint + memoryHint;
```

`memoryHint` 由 `injection.ts` 组装，**硬预算 3000 token**：

```
## 记忆
### 全局（用户偏好与通用规范）        ← pinned global，预算 ~1000
### 项目记忆（workspace 规范）        ← pinned workspace，预算 ~1500
### 本会话背景摘要                    ← session_summaries（有则注入），预算 ~500
### 可检索记忆目录                    ← 非 pinned 各层一行式目录（kind + 前 30 字），预算 ~500
（超预算按 updated_at 截断，尾注「另有 N 条可用 memory_search 检索」）
```

- **每轮现拉**：UI 修改下一条消息即生效；warm runtime 间最终一致
- **子 agent 语义**：注入全局 + 项目常驻（干活也需要规范），不注入会话摘要/会话记忆——与现有 fresh-session 设计（parentStreamSessionId 非空不拉房间历史）对齐
- **检索型不占正文预算**：只给目录行，按需 `memory_search`

### 6.4 自动提取管线（主进程 memory/extraction.ts）

**触发点**（v2.2 实现前两个）：

1. 任务完成：task `final` 事件 / task_reply `completed`（挂 RouterService 既有事件桥）
2. 会话轮次：某会话用户消息累计 ≥20 轮；**去抖**：同一会话 10 分钟内不重复提取
3. （预留）应用空闲

**执行流**（全部异步后台，绝不阻塞会话/任务主链路）：

```
拉取窗口（getConversationContext 最近 50 条）
  → 主进程非流式 LLM 调用（复用 im/session-naming.ts 模式；
     provider 取该会话最近发言 agent 的 provider，无法解析则跳过本轮）
  → ADD-only 提取 prompt（Mem0 代码验证模式：只产候选，不做 UPDATE/DELETE，降低幻觉）
  → 输出候选 JSON：[{kind, content, tags, confidence}]
  → 逐条去重：候选与同 scope 既有记忆 BM25 相似检索（top3）
     · 相似度超阈值 → 跳过 + 日志（v2.2 保守策略，不做自动合并）
     · 新知识 → saveMemory(source='auto', pinned=0, confidence=0.7)
```

- 提取产出一律检索型（pinned=0），用户在 UI 复核后可置顶升常驻——**人是最終质量过滤器**（ChatGPT/VS Code 共同闸门）
- **长会话压缩（同一 LLM 调用的第二产出）**：会话消息数 >40 时顺带产出滚动总结（覆盖：目标 / 已做决策 / 未完成 / 关键文件与标识符——与现有 `compact` 工具总结要求同构），覆盖更新 `session_summaries` 并推进 `covered_until` 游标；既有 `compact` 内联工具保留不动（chat loop 内应急），其产出的 summary 文本经后续消息被管线捕捉
- 成本控制：单次提取 = 一次 LLM 调用（用户 provider token）；全局开关 + 去抖窗口

### 6.5 检索（BM25）

```sql
SELECT m.* FROM memories_fts f
JOIN memories m ON m.rowid = f.rowid
WHERE memories_fts MATCH ?          -- 查询词经 tokenizeForIndex 生成（与写入侧同源）
  AND (m.scope='global'
    OR (m.scope='workspace' AND m.workspace_id=?)
    OR (m.scope='session'  AND m.session_id=?))
ORDER BY bm25(memories_fts) LIMIT ?
```

scope 过滤实现「全局 + 本 workspace + 本会话」三层并集。规模预期 <50k 条，FTS5 B-tree 检索 <10ms。

## 7. 接口设计

### 7.1 MemoryProvider 扩展（兑现既有预留位）

```typescript
interface MemoryProvider {
  // 既有五个方法签名不动（getTaskContext / getConversationContext /
  // getAgentContext / getUserContext / getWorkspaceContext）
  // getAgentContext / getUserContext 由新实现真实化（读 preference/kind 条目），调用方无感

  // v2.2 新增：
  getPinnedContext(opts: { workspaceId: string; sessionId: string | null }): Promise<PinnedMemoryView>;
  searchMemories(query: string, scope: { workspaceId: string; sessionId: string | null }, limit?: number): Promise<MemoryEntry[]>;
  saveMemory(input: SaveMemoryInput): Promise<MemoryEntry>;
  deleteMemory(id: string): Promise<void>;
}
```

`PinnedMemoryView` 携带裁剪后各段文本 + 被截断条数（供注入格式化与测试断言）。

**分层规则（消除歧义）**：`storage/memories/repo.ts` 是唯一数据层（CRUD + FTS 双写）；`MemoryProvider` 是面向 runtime 子进程的消费抽象（读侧 + agent 工具写侧），包装 repo；主进程 IPC 处理器直接用 repo（用户 UI 全权路径，含 update）。三层各司其职，写路径最终都收敛到 repo 单一事务。

### 7.2 IPC 契约（memory:* 命名空间）

```
memory:list(scope: {kind:'global'} | {kind:'workspace', workspaceId} | {kind:'session', sessionId},
            filter?: {kind?, tags?, source?, q?})        → MemoryEntry[]
memory:save(entry: {scope, kind, content, tags?, pinned?}) → MemoryEntry
memory:update(id, patch: {content?, tags?, pinned?})      → MemoryEntry
memory:delete(id)                                          → {ok:true}
memory:search(q, scope?, limit?)                           → MemoryEntry[]
memory:exportMarkdown(scope)                               → {filename, content}（复用导出下载模式）
memory:setEnabled(enabled: boolean)                        → {ok:true}（总开关，存 settings）
```

renderer `ipc/types.d.ts` 与 electron 端结构对齐（跨进程独立定义惯例）；修改两 workspace 均 typecheck（momo-boundary-rules）。

### 7.3 记忆管理 UI（设置独立界面扩展）

- 设置页新增「记忆」入口：全局 / 工作空间（选择器）两层 tab；会话层从会话详情入口进入
- 列表：kind/tag/source 筛选 + 搜索框（走 memory:search）；条目行内编辑/删除/置顶开关
- 总开关 + 提取开关（关闭原因提示：provider 未配置等）

## 8. 错误处理

| 故障 | 行为 |
|---|---|
| 提取 LLM 调用失败 / 超时 | 静默记日志，本轮放弃，下个触发点自然重试；不影响任何会话/任务 |
| Provider 未配置或无 key | 提取与会话压缩停用（设置页显示原因）；agent 工具与手动管理不受影响（纯 DB） |
| FTS 双写失败 | 与主表同事务整体回滚——主表与索引永不漂移 |
| 注入超预算 | 按 updated_at 截断 + 尾注，绝不硬塞 |
| 提取输出坏 JSON | 容错解析（逐行/逐对象扫描），可解析条目照常入库，其余丢弃 + 日志 |
| jieba 加载异常 | 启动时一次 `cut()` 冒烟校验，失败 fail-fast（环境级错误，不静默劣化检索质量） |
| 多进程并发写 | WAL + 短事务（既有模式），注入每轮现拉最终一致 |

## 9. 安全与主权

- 用户主权：`source='user'` 条目对 agent 工具只读；UI 中用户对一切来源条目最高权
- 记忆总开关：一键停止「注入 + 提取」（紧急刹车），DB 保留
- 每 agent 可禁：agent 定义 `deniedTools` 可禁 `memory_*`
- 审计完整：agent 写路径走既有 `logToolCall`；提取与 IPC 写入走 `logger`（含批次 id）
- 不进 LAN 分享：记忆 payload 不加入 p2p resource-catalog 协议
- 导出 Markdown 仅含记忆内容，不含任何凭据

### 11.2 保真度要求（momo-test-rules）

- Mock 构造仿真真实运行时语义：provider 用 `__setMemoryProviderForTest` 注入真实 SQLite 实现（内存库）而非全 mock 接口
- 错误路径专项：上表每行至少一个失败注入用例（LLM 失败/FTS 失败/无 provider/坏 JSON）

### 11.3 契约锁（momo-boundary-rules）

- 分词同源：tokenize-contract 测试锁死写入/查询两侧同函数
- IPC 双端类型：`renderer/src/ipc/types.d.ts` 与 electron 端结构对齐，两 workspace typecheck 进 CI
- MemoryProvider 接口演进不破坏既有五个调用方（getTaskContext 等签名冻结）

## 12. 性能预算

- 注入现拉（pinned 全量 + 摘要单行 + 目录行）：目标 <5ms/轮
- 检索：<10ms @50k 条
- 提取：后台异步单次 LLM 调用（输入 ~50 条消息窗口），用户无感
- 存储：50k 条 × 平均 300 字符 ≈ 15MB，FTS 索引 +30%——对 SQLite 无压力
