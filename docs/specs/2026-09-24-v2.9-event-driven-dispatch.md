# v2.9 事件驱动 Dispatch（followup 异步化 + 回执自动送达 + 心跳死亡检测）

- 日期：2026-09-24
- 状态：已实施（代码已合入工作区）
- 上游：v2.8.0 Orchestration 元语（followup / bg / gather / status / cancel）
- 背景问题：主机会话实测（session e7f8ec7e）暴露 followup 盲等三盲区 + 回执截断三根因（§6）

## 1. 问题定义

v2.8 的 dispatch 族在 PM（leader）侧是**同步阻塞模型**，存在三个结构性盲区：

| 盲区 | 实测表现（会话记录证据） |
|---|---|
| 发送前 | `executeFollowup` 校验只看本链 pending，不知道目标子 agent 是否在忙别的链 / 已崩溃 |
| 等待中 | followup 同步盲等最长 9 分钟（3+6 渐进超时）；子 agent 中间状态只进 renderer，PM 零感知 |
| 超时后 | 超时文案「请直接查看该 agent 的回复」——PM 没有任何查看子 agent 消息流的工具，死循环；dispatch_gather 尾部挂起 10 分钟 |

架构根因：**runtime 子进程每轮 task-end 即退出**——PM 子进程内的
pendingReplies / bgHandles 状态不跨轮存活；子 agent 迟到回执在
RouterService.notifyTaskReply 侧因无活跃子进程被静默丢弃；task_reply 的
in_progress 状态与 progress_pct 字段自 v1.4 定义以来从未有生产者。

## 2. 设计总览

三块基石，全部落在主进程（跨轮真相上移）：

```
┌─ 子 agent 进程（runTaskChatLoop）─────────────────────────────┐
│ dispatch 任务：60s 心跳 in_progress task_reply（首拍立即发）    │
└──────────────────────┬────────────────────────────────────────┘
                       ↓ internal-event-bridge
┌─ 主进程 RouterService ────────────────────────────────────────┐
│ routeDispatch   → DispatchRegistry.register（在途重复轮拒绝）   │
│ routeTaskReply  → heartbeat / settle + 投递判定                 │
│ sweepOnce(60s)  → 心跳静默 >3min 判死 → synthetic failed        │
│ deliverChainResult → dispatch-result 消息行 + routeUserChat     │
│                     （systemKickoff 唤醒 PM 新回合）            │
│ AgentRunner.onIdle → markPmIdle（在途链 awaitWake 快照）+ 补投  │
└────────────────────────────────────────────────────────────────┘
```

### 2.1 DispatchRegistry（新模块 `agent/dispatch-registry.ts`）

主进程跨轮链真相源，taskId → `DispatchChainHandle`：
`{pmAssignmentId, subAssignmentId, sessionId, subStreamSessionId, pmStreamSessionId,
isFollowupRound, status: in_flight|done|cancelled, outcome, body, toolCallsUsed,
startedAt, lastHeartbeatAt, awaitWake, delivered, round}`。

- register：routeDispatch 统一注册（sync / bg / followup）；同链 in_flight
  重复注册返回 false（重复轮拒绝）；settle 后复用 round+1
- heartbeat：in_progress 续命 lastHeartbeatAt
- settle / cancel：幂等终态翻转（needs_input 归 failed，与 BgHandle.outcome 同义）
- markPmIdle：PM 空闲快照——该 PM 全部在途链置 awaitWake
- takeDeliverable：`(isFollowupRound || awaitWake) && done && !delivered`
  的一次性取走（标记防重复唤醒）
- sweepDead：`now - lastHeartbeatAt > 3×HEARTBEAT_INTERVAL_MS` 判死
- 纯逻辑（无计时器/IPC/DB，时钟可注入）；settled 容量 CHAIN_SETTLED_CAP=64 驱逐

### 2.2 心跳契约（子进程侧）

`startDispatchHeartbeat`（runtime-entry 导出）：dispatch 任务启动即发首拍
in_progress（注册即活——消除排队/首 LLM 慢的误判窗口），此后每 60s 一拍
（HEARTBEAT_INTERVAL_MS 与 registry 共享常量源），终态回执发送前停止。
载荷：`{status:'in_progress', body:'子任务运行中（已用 N 次工具调用）',
tool_calls_used, progress_pct(有预算时, <100 封顶), reply_to}`。

心跳同时回流 PM 子进程（armDispatchTimer 重置）——**活链永不被 9 分钟墙误杀**，
死链约 3 分钟确诊（sweepDead → synthetic failed → 同步等待立即 reject）。

### 2.3 followup 异步化

`executeFollowup` 从 `async → Promise<{body, toolCallsUsed}>` 改为**同步返回
送达确认字符串**。校验三连保留，校验 b 扩展 `inFlightFollowups`（子进程侧
在途集：同批并行重复追问同步拒绝；任意回执到达即清除）。派发 content 新增
`followup_round: true`（DispatchContent 新字段，parseDispatchEvent 两端成对）。

终态回执经「恒投递」路径自动送达（见 2.4）——PM 无需等待、无需 gather。

### 2.4 回执自动送达（注入唤醒）

投递条件（dispatchRegistry.takeDeliverable）：
1. **followup 轮恒投递**（PM 显式在等答案）
2. **非 followup 链在 PM 空闲快照（awaitWake）后翻转的投递**——覆盖
   「PM 回合结束时 bg 仍在途 → 完成后回执不丢」的挂起场景
3. PM 回合内翻转的非 followup 链不投递（子进程 bgHandles 已收割，正常流）

投递动作 `deliverChainResult`：
1. 落库 dispatch-result 消息行：`sender='owner'`、`taskId=链 ID`（行因此
   进链历史——后续 followup 的 rebuildSubConversation 天然聚合本轮结果）、
   `streamSessionId` 单点生成
2. `routeUserChat(systemKickoff: true)` 唤醒 PM 新回合——输入即回执全文

时序：终态到达时 PM 空闲 → 立即投递；PM 忙碌 → onIdle 边沿补投
（AgentRunner 活跃归零回调 → notifyRunnerIdle 模块级注入通道 →
router-bootstrap 绑定，避免构造期循环依赖）。连续投递自然级联。

### 2.5 重复轮拒绝的反馈闭环

routeDispatch 注册失败（同链在途）绝不静默：PM 回合内经 `runner.steer`
向 PM 当前流注入系统提示（「回执完成后会自动送达，无需重发」）；PM 空闲
则记日志（下一轮追问由主进程链态兜底拒绝）。abort_dispatch /
dispatch_cancel → registry.cancel（cancelled 恒不投递）。

### 2.6 文案修复

同步 dispatch 超时文案从「请直接查看该 agent 的回复」（写给人类、PM 无
工具可执行）改为 agent 可操作动作链（等待自动送达 / dispatch_bg 重派）。

## 5. 已知边界（后续迭代）

- **PM 回合内翻转但未 gather 的 bg 链**：PM 主动结束回合放弃收割 → 不补投
  （尊重 PM 的显式选择；gather 超时 pending 的挂起场景已由 awaitWake 覆盖）
- **WarmPool 排队 >3 分钟**的极端场景可能心跳误判（首拍已大幅收窄窗口）
- registry 不跨应用重启（与子进程态同语义）；`dispatch_status` 查询跨轮
  句柄是 v2.10 候选（当前跨轮结果靠注入送达，无需查询）
- 心跳重置同步渐进计时器后，「活着但无限慢」的同步 dispatch 等待不再有

## 6. 结果完整性（P0 三项，同日追加）

§1-§5 解决「回执能不能到 PM 手里」；本节解决「回执里装的是不是完整结果」
（会话 e7f8ec7e 实测：14 项报告的回执只剩 1 行收尾摘要、另一份缺整节）。

### 6.1 分段重组进终态回执（P0-1）

根因：`task_complete` 发段后 `accumulatedText` 重置，而终态 `finalText` 只取
末段尾巴——已持久化的前段从不进 `task_reply.body`。

修复（runtime-entry runChatLoop）：`completedSegments: string[]` 收集全部
已持久化段；`buildFinalText(fallback, ...extras)` 统一七个出口（正常收尾 /
重复检测 / 预算耗尽 / 分段上限 / 中断 ×3）的终态组装 = 全部段（task_complete
顺序）+ 末段累积 + 出口额外段（分段上限时未持久化的 summary），空段过滤、
双换行连接。实测语义锁定：task_complete 同轮的 text 在进工具循环前已消费进
messages——**段内容只经 summary 参数承载**（子 agent 实际行为如此，
dispatch-result-integrity.test.ts 有专项锁）。

### 6.2 outputTokens 透传为 max_tokens（P0-3）

根因：OpenAI 路径请求体完全无 `max_tokens`（依赖模型默认，行为不可预期）；
Anthropic 硬编码 4096/16384；model-catalog 的 outputTokens 从未传给 LLM。

修复（llm-provider.ts + runtime-entry）：`createLLMProvider` opts 增
`maxTokens`；OpenAI chat/chatStream 按配置携带 `max_tokens`（未配置不携带）；
Anthropic 用配置值替换两处硬编码（必填参数，缺省回退旧值；thinking 模式
的 budget+4096 抬升语义保留）。runtime-entry 按 `config.outputTokens > 0`
透传；两项皆缺省时第三参保持 `undefined`（P3 接线锁的旧 wire 形态不变）。

### 6.3 超长回执落盘 + 摘要引用（P0-2）

`spillDispatchBodyIfNeeded`（runtime-entry 导出）：dispatch 终态回执超
`DISPATCH_BODY_SPILL_THRESHOLD_BYTES`（8KB）→ 全文写
`<workspaceDir>/.momo-scratch/dispatch/<chainId>.md`（scratch 约定目录 +
workspace 沙箱内，PM 的 read_file 可 offset/limit 分页读取），body 替换为
「落盘说明（字符数/体积/路径）+ 头部摘录（前 1500 字符）+ 相对路径」。
生产点在子进程发送 task_reply 前（**单点收口**——同步等待、gather 收割、
§2.4 注入送达三种消费路径拿到同一形态）。写盘失败降级回原文（回执绝不因
落盘失败而丢失）；阈值内零开销原样返回。

## 7. Review 修复批次（同日追加）

5-agent 并行 review（目标/QA/质量/安全/上下文）判 FAILED，6 项阻塞按序修复：

### 7.1 B1：OpenAI reasoning 模型参数名分流

catalog 全部 gpt-5/o 系模型（reasoning.kind='effort'）+ outputTokens>0 →
P0-3 透传后必发 `max_tokens` → OpenAI 官方 reasoning 模型硬拒 400（要求
`max_completion_tokens`）。修复：`resolveMaxTokensParam(platform, modelId,
baseUrl)`（model-catalog 导出）——「官方模型名前缀（gpt-5|o[134]）+ 无
自定义 baseUrl」才分流 `max_completion_tokens`；GLM-5/DeepSeek-v4 同为
openai+effort 但走兼容端点，保持 `max_tokens`。经 AgentRuntimeOpts →
parseConfig → llmOpts → createLLMProvider(maxTokensParam) 全链透传，
OpenAI chat/chatStream 按参数名写 body，Anthropic 忽略。11 项判别矩阵 +
2 项 body 键断言锁定。

### 7.2 B2：内部事件身份绑定 + settle 授权

根因：桥（internal-event-bridge）不校验 envelope sender——任意子进程可
伪造他人身份发 dispatch/task_reply，经注入路径冒充用户（sender='owner' 行）
写入任意会话并唤醒任意 PM。修复三层：
1. 桥层绑定：runtime-spawner 传入 spawn 闭包的 `runtimeConfig.agentUserId`，
   sender 不符的内部事件直接丢弃（生产恒传；测试直连缺省不校验）
2. routeDispatch：sender 反查 assignment（workspace_agent_members，限会话
   workspace）与 dispatch_from 不符 → 丢弃
3. applyRegistryReply settle：sender 反查 ≠ 链 subAssignmentId → 忽略
   （反查不可解析时降级放行——桥层绑定已保证 sender 不可伪造，降级只影响
   授权粒度；synthetic sweep 路径不经此校验）

### 7.3 B3：taskId 消费点加固

- routeDispatch：taskId 形状门 `/^[A-Za-z0-9_-]{1,64}$/`（拒路径穿越/
  超长）——注册表键的上游
- spill 文件名：同形状门，非法 → fallback `unsafe-<uuid>`（原文仍完整落盘）
- steer 拒绝提示与 deliverChainResult 头部：taskId 剥离控制字符再插值
  （防伪造消息结构注入 PM 上下文）

### 7.4 B5：inFlightFollowups 仅终态清除

心跳清除在途标记 → 子/主校验漂移：PM 二次追问拿到「已送达」确认后被主
进程拒绝 + steer 丢失 → 追问静默丢失。修复：仅终态
（completed/failed/needs_input）清除；心跳保持标记。

### 7.5 B6：sweepOnce .catch + 投递串行化

- sweepOnce 的 notifyTaskReply 补 `.catch`（主进程 unhandled rejection 面）
- tryDeliver 重写为 per-runner 串行循环：`takeNextDeliverable` 单条取走 +
  await deliverChainResult + 每轮 busy 重查——一回合一条，余链留给下一个
  idle 边沿（级联），消除同会话并发 PM 回合与 session-lane 覆盖

### 7.6 B4：强制退出补投 + 复用前补投 + 文案诚实化

- AgentRunner 收尾按 lastFinish 判 forcedExit（非 stop = 强制截断；崩溃/
  兜底路径恒 true）经 onIdle → onPmIdle → markPmIdle(deliverSettledUndelivered)
  ——强制截断时 done-未投递链补投；正常收尾维持 gather 契约
- handleChildExit 补 idle 边沿（此前崩溃路径不触发）
- routeDispatch 链复用前 `requeueUndelivered` 取快照立即补投上一轮未投递
  回执（不能靠 awaitWake——register 复用重置会抹掉）
- prompt-hints/builtin-tools 文案诚实化：「回合内已完成的结果请先 gather
  再收尾（正常收尾不补投）；强制截断时系统自动补投」

- 回执全文双计：注入行与子 agent 流行在 followup historyPrefix / 导出中
  重复承载全文（需裁定去重策略）
- spill 文件被 followup 下一轮同名覆盖（旧引用失效）；registry round 重启

- LAN 广播 / workspace_id / session:message 实时推送与注入行不联动

## 8. 第二轮 review 修复（同日追加）

5 泳道复审（2 PASS / 3 FAIL）判 FAILED，三项新阻塞 + 一项 edge 按序修复：

### 8.1 R1（CRITICAL）：退出路径 forced 空闲边沿污染

复审发现：warmPool.release() 是 v1 销毁语义（每轮正常收尾 kill 子进程），
exit 事件在正常结束后必然到达 handleChildExit——旧实现无条件补发
maybeFireIdle(true)，导致**每个正常回合都被当作强制截断**：已被同步消费
（executeDispatch 返回值 / gather）的 done-未投递链被系统性重复补投，
「正常收尾不补投」契约全面失效（质量+上下文双泳道独立收敛）。

修复（agent-runner.ts）：handleChildExit 清理循环记 `cleanedAny`（本次退出
是否确实中止了活跃任务）——仅 `cleanedAny && !shuttingDown && activeTasks
为空` 时触发 forced 边沿；正常收尾后的例行 kill、关机期 kill 不触发。
maybeFireIdle 文档注释同步修正（电平触发，非边沿锁存）。回归锁：三态用例
（崩溃触发 / 例行退出不触发 / 关机不触发）。

### 8.2 R2（HIGH）：sender 校验 fail-closed（三态）

复审发现：旧 resolveSenderAssignment 二值降级（null=放行）把「环境性 DB
失败」与「攻击者可主动安排的反查落空」混为一谈——被入侵子进程用自己真实
sender + 伪造 envelope sessionId（跨 workspace 会话 / 不存在的会话 → 反查
必然落空）即可绕过 dispatch_from / subAssignmentId 校验，完整复活 round-1
HIGH-A（owner 行注入任意会话 + ensureRunner 唤醒任意 agent + 第三方链
settle 劫持）。

修复（router-service.ts）：resolveSender 改三态——
- `ok`：反查成功（assignment 严格比对，不符丢弃）
- `degrade`：环境性 DB 失败（getSession/getDb 抛错）→ 降级放行 + 日志
- `reject`：会话不存在 / 发送者非会话 workspace 成员 / 非法身份
  （owner/空）→ **一律丢弃**（这些状态可被攻击者经 sessionId 安排）

routeDispatch 与 applyRegistryReply（settle + 心跳）两处消费。回归锁：
跨身份冒充 / 幽灵会话 / 跨 workspace 外来者 / 第三方 settle 劫持四用例
+ 正身回执正常 settle。

### 8.3 R3（MAJOR）：复用前补投绕过串行化

复审发现：routeDispatch 的 B4(ii) 补投直接 `deliverChainResult(...)`——
但派发时 PM 必然在回合中，直接投递绕过 busy 门与 delivering 守卫，在 PM
回合内并发拉起第二条顶层流（session-lane 覆盖——恰是 B6 要消除的形态）。

修复（router-service.ts）：新增 `pendingDeliveries` 队列（pmAssignmentId →
快照列表）——复用前补投入队，由 tryDeliver 串行化循环优先消费（busy 时
挂起，idle 边沿逐条投递）。回归锁：忙碌期复用 → 不并发投递，idle 边沿送达。

### 8.4 R4（EDGE）：resolveMaxTokensParam platform 缺失启发式

旧供应商行 platform 列可能为空——旧实现 `platform !== 'openai'` 直接回
max_tokens（官方端点 gpt-5 仍 400）。改为：baseUrl 非空 → max_tokens；
